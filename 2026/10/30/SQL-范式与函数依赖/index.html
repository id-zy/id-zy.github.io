关系数据库设计：候选键、函数依赖与 1NF 到 4NF

一张表设计得不好，最先出问题的不是查询慢，而是数据打架：同一个系主任在两个学生行里写了两个名字，改了一个忘了另一个。这类问题的根源是「一个关系模式里塞了本该分开的两件事」，而范式就是判断「该不该拆、拆到哪一步」的尺子。

这篇是按「依赖 → 键 → 范式 → 多值依赖 → 分解」的顺序写的，和实际做题的推导链条一致。注意：这一篇是纯理论，没有 SQL 可以实跑——所有例题都是手算的，步骤全部列出来，你可以逐步复核。

一、规范化要消灭什么

先明确目标，否则范式只是死记的四条定义。设计不良的关系模式会带来三类异常：

异常 表现 例子
插入异常 想插入一条信息，却发现没地方放 只有「学生选课」表，新开的课程还没有学生选，就插不进去
删除异常 删一条记录，顺手丢了别的事实 删掉最后一个选这门课的学生，课程信息一起没了
更新异常 同一事实存了多份，改漏一处就不一致 系主任换人，要改几十行，漏一行就出现两个系主任

三者共同的根源是冗余：同一事实被重复存储。规范化的做法是把关系模式分解，让每个事实只存一处。

代价也要说清：拆得越细，查询时的 JOIN 越多。所以工程上不是「范式越高越好」，而是「先到 3NF，性能确有需要时再有意识地反范式化」（数仓的宽表就是主动反范式）。

二、函数依赖与 Armstrong 公理

函数依赖是什么

X → Y 表示：在这个关系的任意两个元组里，只要 X 上的值相同，Y 上的值必然也相同。

注意它是语义约束，不是从数据里统计出来的规律。学号 → 姓名 成立，是因为业务规定一个学号只对应一个人；哪怕现在表里恰好没有重名，也不能反过来说「姓名 → 学号」成立。

三条公理

公理 内容 直觉
自反律 若 Y ⊆ X，则 X → Y 知道自己的一切
增广律 若 X → Y，则 XZ → YZ 两边同加属性仍成立
传递律 若 X → Y 且 Y → Z，则 X → Z 链条可以接起来

由这三条能推出三条常用规则：合并律（X → Y、X → Z 得 X → YZ）、分解律（X → YZ 得 X → Y 与 X → Z）、伪传递律（X → Y、WY → Z 得 XW → Z）。

属性闭包：判定依赖是否成立的主力工具

题目问「AC → D 成立吗」，最可靠的做法不是硬推，而是算 (AC) 的属性闭包——从 AC 出发，把所有能被它推出来的属性一路收进来：

  1. 初始化 result = AC
  2. 扫一遍依赖集，凡是左边已经被 result 覆盖的，把右边也并进 result
  3. 重复到 result 不再变化
  4. 若 D 在 result 里，则 AC → D 成立

用 F = {C → AD, AB → C, C → B} 验一遍：

同样的结论也能用公理直接推：C → AD 分解出 C → D，两边增广 A 得 AC → AD，再分解得 AC → D。两种解法都要会——闭包适合编程实现、适合复杂依赖集；公理推导适合考试时手写三行。

为什么不直接求依赖集闭包 F+？因为它可能是指数级规模，而属性闭包只算需要的属性集，代价是多项式级。这是「闭包」这个词最容易被问住的地方。

三、候选键求解：先分类，再验闭包

四个概念先分清

概念 定义 关系
超键 能唯一标识元组的属性集（K → U） 最宽
候选键 极小的超键（去掉任一属性就不再是超键） 超键的子集，可能有多个
主键 从候选键中挑一个 候选键之一
外键 本关系的属性集是另一关系的主键 跨表引用

关键区别就一句：候选键必须极小。{学号, 姓名} 能唯一标识学生，但不是候选键，因为 {学号} 就够了。

求解四步：L / R / LR / N 分类法

把每个属性按「在依赖里出现的位置」分类：

  • L 类：只出现在 → 左边
  • R 类：只出现在右边
  • LR 类：两边都出现
  • N 类：两边都没出现

结论：候选键一定包含所有 L 类和 N 类属性，再按需补若干 LR 类属性；R 类属性永远不在候选键里（它们推不出别人）。

推理很直白：只出现在左边的属性，没有任何依赖能推出它，所以必须由候选键自己带上；两边都不出现的属性同理，只能显式包含。

例一：三个候选键的情况

U = {A,B,C,D}，F = {AB → C, C → D, D → A}。

先分类：L 类 = B（只在左边）、R 类 = 无、LR 类 = A, C, D、N 类 = 无。

底座是 B，但它单独推不出全集：B+ = B。于是逐个补 LR 类属性试闭包：

组合 闭包过程 闭包 是超键 极小
AB AB → C 得 ABC；C → D 得 ABCD ABCD ✅ ✅
BC C → D 得 BCD；D → A 得 BCDA ABCD ✅ ✅
BD D → A 得 BDA；AB → C 得 BDAC ABCD ✅ ✅
AC C → D 得 ACD；无依赖可再用 ACD ❌ —
CD D → A 得 CDA ACD ❌ —

所以候选键是 AB、BC、BD 三个。极小性都要单独验：A+ = A、B+ = B、C+ = ACD、D+ = AD，四个单属性都推不出全集，因此上表三个组合都是极小的。

顺便注意 BCD 这个组合：BCD+ = ABCD 确实是超键，但 BC+ = ABCD 且 BC ⊂ BCD，所以 BCD 不极小，不是候选键。这就是「超键多、候选键少」的具体样子。

例二：单候选键的情况

U = {A,B,C,D}，F = {B → C, B → D}。

L 类 = A, B；R 类 = C, D。

底座 AB：AB+ 从 AB 出发，B → C 得 ABC，B → D 得 ABCD，闭包等于全集。再验极小：A+ = A、B+ = BCD，都不是全集，所以候选键就是 AB，唯一一个。

最容易错的地方

「L 类属性的组合一定是候选键」是错的。 例一里 B 是唯一的 L 类属性，但 B+ = B，它不是超键。必须算闭包验证，而且验完还要回头查极小性——两件事缺一不可。

四、1NF 到 BCNF：每一级拆掉什么

四级范式的本质是一条「逐级消灭更隐蔽的依赖」的链：

范式 消除的依赖 判断方法 反例
1NF 属性不可再分（表里套表） 有没有复合属性 / 多值属性 (学号, 姓名, {课程号, 成绩})
2NF 非主属性对候选键的部分依赖 候选键是单属性时必然满足；复合键时看有没有属性只依赖键的一部分 SCG(学号, 课程号, 系名, 系主任, 成绩)，系名 只依赖 学号
3NF 非主属性对候选键的传递依赖 找 候选键 → X → A（X 不是候选键，A 非主属性） SD(学号, 系名, 系主任)：学号 → 系名 → 系主任
BCNF 决定因素不是超键的非平凡依赖（含主属性之间的） 每个 X → Y 的 X 是否都是超键 TCS(教师, 课程, 学生)，T → C

为什么 3NF 不等于 BCNF

这是最经典的追问。差别在主属性：3NF 只管非主属性，允许主属性之间存在「决定因素不是超键」的依赖；BCNF 一律不许。

R(A,B,C)，F = {AB → C, C → B}：

  • 候选键是 AB 和 AC（AB+ = ABC，AC+ = ACB），所以 A、B、C 全是主属性。
  • 没有非主属性，2NF、3NF 自动满足。
  • 但 C → B 里 C+ = CB ≠ ABC，C 不是超键 → 违反 BCNF。

一句话记住：3NF 只看非主属性，BCNF 看所有决定因素。所以 BCNF ⊂ 3NF（满足 BCNF 一定满足 3NF，反之不然）。

五、多值依赖与 4NF

函数依赖表达不了的情况

看这张表 Course(教师, 课程, 参考书)：

教师 课程 参考书
王老师 数据库 《DB原理》
王老师 数据库 《SQL指南》
王老师 操作系统 《OS概念》
王老师 操作系统 《Linux编程》

语义上「课程」和「参考书」是两件独立的事：王老师教两门课，每门课都有各自的书，但书和课之间没有依赖关系。

问题在于：这张表里没有任何函数依赖（除了平凡依赖），所以按 FD 分析它「没有冗余」——可它明明冗余得厉害：王老师教「数据库」这件事存了两遍（每本书一次）。一旦要加第三本参考书，得插两行（两门课各一行）；要删「操作系统」这门课，会连带把《OS概念》《Linux编程》的信息一起删掉。

多值依赖：X ↠ Y

记作 X ↠ Y，含义是：当 X 的值确定后，Y 的取值集合就确定，并且 Y 与剩下的属性 Z = U - X - Y 自由组合。

用一句话概括：同一个 X 下，Y 的每个值都要和 Z 的每个值配一遍。上面那张表里 教师 ↠ 课程 和 教师 ↠ 参考书 同时成立——这正是「4 行 = 2 门课 × 2 本书」的由来。

几条性质值得记住：

性质 内容
互补性 X ↠ Y 成立则 X ↠ (U - X - Y) 也成立
FD 是 MVD 的特例 X → Y 成立则 X ↠ Y 成立
合并 X ↠ Y 且 X ↠ Z，则 X ↠ YZ
传递 X ↠ Y 且 Y ↠ Z，则 X ↠ (Z - Y)

4NF：把决定因素的要求提到 MVD 上

范式 依赖类型 要求
2NF / 3NF FD 消非主属性的部分 / 传递依赖
BCNF FD 每个非平凡 FD 的决定因素是超键
4NF MVD 每个非平凡 MVD 的决定因素是超键

上面 Course 表里 教师 ↠ 课程 的决定因素 教师 不是超键（王老师只对应一部分行）→ 违反 4NF。拆法很自然：

  • R1(教师, 课程)
  • R2(教师, 参考书)

拆完之后，「加一本书」只需在 R2 插一行，不再随课程数翻倍——冗余消失了。

因为 FD 是 MVD 的特例，所以 4NF 一定满足 BCNF，反过来不成立。这条包含关系是面试的高频点。

六、模式分解：无损连接与依赖保持

拆表不是随便拆。一个正确的分解要满足两条性质，而这两条经常不可兼得。

性质一：无损连接

分解后对子模式做自然连接，必须能精确还原原关系——不丢元组，也不多出原本不存在的元组。

二元分解有个好用的判据：把 R 拆成 R1、R2 时，若 R1 ∩ R2 → R1 或 R1 ∩ R2 → R2 成立，则分解是无损的。也就是说，两个子模式的公共属性必须能决定其中一个子模式。

性质二：依赖保持

原依赖集 F 里的每一条，都要能在某个子模式上被检查。否则约束就"漂"了——数据库里还在，但没有一张表能验证它。

两种算法，两种取舍

算法 目标 结果
3NF 合成法 按最小覆盖分组，左部相同的依赖并成一张表；若结果里没有候选键，补一张候选键表 无损 + 保持依赖，可能残留主属性的部分依赖
BCNF 分解法 递归找违反 BCNF 的依赖，按它把模式一分为二 无损，但可能丢依赖

例题一：BCNF 分解会丢依赖

R(A,B,C,D)，F = {A → B, B → C}。

  1. 求候选键：(AD)+ = ADBC，所以 AD 是候选键。
  2. A → B 的决定因素 A 不是超键 → 违反 BCNF。
  3. 按 A → B 拆：R1(A,B)、R2(A,C,D)。
  4. R2 里仍有 A → C（A 在 R2 中不是超键）→ 再拆成 R21(A,C)、R22(A,D)。
  5. 最终：R1(A,B)、R21(A,C)、R22(A,D)，三张都满足 BCNF。

问题来了：原来那条 B → C 丢了。R1 只有 A → B，R21 只有 A → C，R22 什么都没有——没有任何一张表能检查 B → C。这就是「为了 BCNF 牺牲依赖保持」的代价。

例题二：3NF 合成法两全

R(A,B,C,D,E)，F = {A → B, BC → D, D → E}。

  1. 按左部分组：R1(A,B)、R2(B,C,D)、R3(D,E)。
  2. 求候选键：(AC)+ = ACBDE = ABCDE，AC 是候选键。
  3. AC 没有出现在任何子模式里 → 补一张 R4(A,C)。
  4. 最终四张表，无损连接 + 依赖保持，且都满足 3NF。

这就是工程上普遍做到 3NF 就收手的原因：它能一次拿到两个好性质，而 BCNF 要拿「更强的范式」去换「可能丢约束」。

七、判据速查

做题和读表设计时的对照表：

你看到的症状 问题所在 该做什么
单元格里塞了逗号分隔的多个值 违反 1NF 拆成多行
复合主键下，某列只依赖其中一部分 部分依赖，违反 2NF 把这列拆到只含该部分的表
A → B → C 里 B 不是键 传递依赖，违反 3NF 把 B → C 单独成表
每个 FD 的决定因素都不是超键，但都是主属性 违反 BCNF 按该依赖二分拆解
一个 X 下出现「两个独立集合的笛卡尔积」 多值依赖，违反 4NF 按 MVD 拆成两张
拆完自然连接变多了行 分解不是无损的 检查公共属性能否决定某一侧

判断一个关系属于第几范式，顺序固定：求候选键 → 查部分依赖 → 查传递依赖 → 查决定因素是否超键 → 查 MVD。

八、面试会追问什么

追问 答法要点
为什么求闭包而不求 F+？ F+ 可能指数级；属性闭包是多项式代价，只算需要的属性
候选键一定是 L 类属性吗？ 候选键必含所有 L、N 类属性，但 L 类组合不一定是候选键，必须验闭包 + 验极小性
3NF 和 BCNF 差在哪？ 3NF 只管非主属性，BCNF 管所有决定因素；R(A,B,C)、F={AB→C, C→B} 是 3NF 非 BCNF 的标准反例
为什么工程上做到 3NF 就够？ 3NF 能同时保证无损连接与依赖保持；BCNF 更强但可能丢约束
无损连接怎么判？ 二元分解看 R1 ∩ R2 能否决定 R1 或 R2；多元分解用表格法（Chase）
为什么需要 4NF？ FD 表达不了属性间的独立重复，只用 FD 分析会把有冗余的表误判为「无冗余」
4NF 和 BCNF 的关系？ 4NF ⊂ BCNF；因为 FD 是 MVD 的特例
反范式化什么时候可以做？ 读多写少、JOIN 成为瓶颈、且冗余的一致性有别的机制保证（如定时任务、数仓重跑）

小结

  • 规范化的目标是消灭插入 / 删除 / 更新三类异常，手段是分解以消除冗余；代价是 JOIN 变多，所以工程上「先 3NF，再按需反范式」。
  • 函数依赖是语义约束，不是从数据统计出来的；判断 X → Y 是否成立，靠算属性闭包 X+，而不是硬推公理。
  • 候选键是极小超键：先按 L / R / LR / N 分类，取 L+N 作底座，补 LR 试闭包，最后必须验极小性。例一里 BCD 是超键却不是候选键，就是这个道理。
  • 四级范式逐级消灭：1NF 消表中套表、2NF 消部分依赖、3NF 消传递依赖、BCNF 消「决定因素非超键」。
  • 3NF ≠ BCNF：差别在主属性。R(A,B,C)、F={AB→C, C→B} 满足 3NF 但违反 BCNF，因为 C → B 的 C 不是超键。
  • 多值依赖处理「两个独立集合的笛卡尔积」；FD 是 MVD 的特例，所以 4NF ⊂ BCNF。
  • 分解要满足无损连接（自然连接能还原）与依赖保持（每条依赖都有表可检查）；3NF 合成法两者兼得，BCNF 分解法可能丢依赖（B → C 那条就是典型）。

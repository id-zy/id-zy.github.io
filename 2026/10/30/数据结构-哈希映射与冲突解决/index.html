哈希表：O(1) 不是免费的，它用装填因子和哈希质量来换

哈希表：O(1) 不是免费的，它用装填因子和哈希质量来换

「哈希表查找 O(1)」这句结论几乎人人会背，但它藏了三个前提：哈希函数足够均匀、装填因子足够低、key 在存进去之后不再变。缺了任何一条，O(1) 就退化——最坏情况是 O(n)，和遍历一遍没区别。

这篇从「为什么需要哈希」讲到「工程里怎么用」，代码统一 Python，所有数字都是本机实跑的输出。

一、起点：key 不是下标

数组的 O(1) 靠的是「地址 = 首地址 + i × 元素大小」，前提是下标从 0 到 n−1 连续。

但真实场景里的 key 不长这样：

  • 学号 2023001234
  • 用户名 "chen"（字符串，不是数字）
  • 身份证号（19 位，远超任何数组长度）

这些 key 没法直接当下标用。要么把「key → 下标」这个换算固化下来存下来（这就是哈希表干的事），要么每次都遍历一遍找（O(n)）。

哈希表做的就是加一层映射：

这把「按 key 查找」变成了「按算出来的下标访问数组」，于是 O(n) 变 O(1)。代价是这个映射不可能是单射——不同 key 可能算出同一个下标，这就是冲突，后面所有复杂度都围绕它展开。

二、哈希函数要满足的三件事

教材给的公式是 address = H[key]，但「能算出地址」远远不够。一个可用的哈希函数要同时满足：

要求 含义 不满足会怎样
确定性 同一个 key 每次算出的值必须一样 存进去就找不回来，表直接废掉
均匀性 结果在值域内尽量均匀铺开 大量 key 挤在少数桶里，退化成链表
计算快 最好是几次乘加、移位 哈希本身成了瓶颈，O(1) 常数项爆掉

三条里最容易忽略的是均匀性。它不取决于 key 有多少，而取决于 key 的分布形态和函数设计是否吻合——下一节的实测就是这个。

三、五种构造方法，除留余数法为什么最常见

教材列了五种：

方法 做法 适合什么 key
直接定址法 H(k) = a·k + b key 连续、范围小，几乎不冲突
除留余数法 H(k) = k mod m 通用，最常用
数字分析法 挑数字里分布均匀的几位 key 位数多、某几位明显更随机
平方取中法 k² 取中间几位 key 每一位都影响结果
折叠法 key 切成等长段相加 key 特别长（如身份证）
随机数法 H(k) = random(k)（伪随机但确定） key 长度不等

工程上绝大多数实现都落在除留余数法上，因为它最简单，且「取模」这个动作本身就能把任意大的整数压到 [0, m) 里。

但 m 取什么值，直接决定冲突率。实测：1000 个 key（全部是 10 的倍数），三种 m 的分布：

三个结果差异巨大，原因很直白：

  • m = 1000：key 全是 10 的倍数，k mod 1000 的公约数也是 10，1000 个 key 只落进 100 个桶，平均每个桶 10 个。
  • m = 1024（2 的幂）：取模等价于「取二进制低 10 位」，key 全是偶数 → 低 10 位的最低位恒为 0 → 只有 512 个桶被用到。
  • m = 1009（质数）：与 10 互质，1000 个 key 一个桶一个，完美。

这就是「除留余数法的 m 要取质数」的全部道理：质数与大多数 key 分布互质，能把 key 里隐含的规律性打散。反过来说，如果你的 key 是自增 ID（1, 2, 3…），取什么 m 都均匀，质数就没有额外好处。

工程实现反而经常用 2 的幂，例如 Java HashMap 用 (n-1) & hash 代替 % n——因为位运算比除法快，而它靠高位扰动（h ^ (h >>> 16)）先把高位的信息混进低位，补上了「只取低位」的缺陷。这是「算法教材选质数」和「工程实现选 2 的幂」的典型分歧，两边都对，前提不同。

四、冲突一定发生：抽屉原理与装填因子

n 个 key 映射到 m 个桶，只要 n > m，必然有桶装了两个以上——抽屉原理，绕不过去。

即使 n ≤ m 也会冲突：把 n 个球随机扔进 m 个格子，期望的碰撞对数是 C(n,2)/m。n=1000、m=1009 时约 495 对，所以「桶数够多就没事」是错觉。

衡量「挤不挤」的指标是装填因子：

  • 链地址法：α 可以大于 1（桶可以挂任意长的链）
  • 开放定址法：α 必须小于 1（元素就存在桶里，桶满了没地方放）

α 是所有性能结论的自变量。下面的实测会看到：α 从 0.5 涨到 0.99，链地址的平均查找只从 1.22 次涨到 1.50 次，线性探测从 1.38 次涨到 19.58 次——差了 13 倍。这就是为什么「选哪种冲突处理方式」比「哈希函数写多漂亮」更影响性能。

五、链地址法（拉链）：冲突了就挂一条链

最简单粗暴：每个桶不是一个格子，而是一个链表的头指针。冲突的 key 依次挂在同一条链上。

优点：

  • 删除干净——链表摘结点，不影响别的 key（对比下一节开放定址的麻烦）
  • α 可以超过 1，不怕元素比桶多
  • 实现简单，冲突多少都能跑

缺点：

  • 每个元素多一个指针开销（存小整数时这个开销比数据本身还大）
  • 链表是离散访问，CPU 缓存不友好（这是它在大数据量下慢于开放定址的主要原因）
  • 极端情况下一条链很长，查找退化成 O(n)

最后这条就是 JDK 8 给 HashMap 加红黑树的原因：当某个桶的链表长度 ≥ 8 且表长 ≥ 64 时，把这条链转成红黑树，最坏查找从 O(n) 降到 O(log n)。长度降到 6 以下再转回链表。门槛设 8 是因为正常哈希下桶长服从泊松分布，长度到 8 的概率已经低到约千万分之六——真到 8 说明哈希质量有问题或遭了哈希攻击，这时候才值得付树的代价。

六、开放定址法：冲突了就换个位置

思路完全不同：所有元素都直接存在桶数组里，冲突时按某种探测序列找下一个空位。

三种探测序列：

方法 探测序列 特点
线性探测 (h + 1) % m, (h + 2) % m, … 最简单，但会产生「一次聚集」
二次探测 (h ± 1²) % m, (h ± 2²) % m, … 缓解一次聚集，但只能探到约一半的格子
双重散列 (h1 + i·h2(k)) % m 步长也由 key 决定，最接近「随机」

一次聚集：线性探测的致命伤

线性探测的问题不是「会冲突」，而是冲突会连成片：一个位置被占，下一个 key 就往后挪；再下一个又往后挪。于是连续的占用块越来越长，任何落进这个块的 key 都要探到底。

实测（m=1000，随机 key）：

读这张表要注意三件事：

  1. 链地址几乎不随 α 变。α 从 0.5 到 0.99，平均探测只从 1.22 到 1.50，与教材公式 1 + α/2（→1.25 和 1.50）完全对得上。因为拉链的查找成本只跟「自己那条链多长」有关，而每条链的期望长度就是 α。
  2. 线性探测在 α 逼近 1 时爆炸。α=0.99 时平均要探 19.58 次，最长连续块 756 个格子——1000 个格子里 756 个连成一片，等于退化成顺序查找。
  3. 小表（m=1000）的抖动明显，α=0.75 和 0.90 的量级关系不像理论那么单调。趋势可信，绝对值别当常数背。

所以开放定址的实际用法必须是「留足余量」：Python dict 在 α 到 2/3 就扩容，Java 的 ThreadLocalMap 用开放定址但只有 16 个槽位、冲突极少。真要 α 逼近 1，只能靠 rehash 扩容。

删除必须打墓碑，否则断链

这是开放定址最容易踩的坑，也是教材必考的点。

get 的终止条件是「撞到空位 = 一定不存在」。那么直接删掉一个元素、把它变成 None，会怎样？

删掉 12 之后，23 明明还在表里，但查找在索引 1 就撞到空位、判定「不存在」。探测链断了。

解决办法只有两个：

  1. 墓碑（tombstone）：删除时不置空，而放一个「已删除」标记。查找时把墓碑当作「继续探测」，插入时可以复用墓碑的位置。
  2. 不留墓碑但重排：删掉后把后面连续的块整体前移一位（有些实现叫 backward-shift deletion）。代价是删除变慢。

墓碑的副作用是积累：墓碑越来越多，查找要跳过一堆墓碑，性能慢慢退化到接近线性。所以实现里通常要在墓碑数超过阈值时整体 rehash 重建。

顺带说：CPython 的 dict 也用了墓碑（源码里叫 DKIX_DUMMY），删除时把槽位标成 dummy，等扩容时才真正清掉。教材上的墓碑不是纸面概念，主流实现里就在用。

七、装填因子真的被实现当真：Python dict 的扩容点

「α 到多少就扩容」不是随便定的。实测 Python 3.13 的 dict，看 sys.getsizeof 在第几个元素时跳变：

把容量代进去就明白了：8, 16, 32, 64, 128, 256 个槽位，对应的可用上限是 5, 10, 21, 42, 85, 170——正好是容量的 2/3（8×2/3≈5.33→5，256×2/3≈170.67→170）。

也就是说：Python 的 α 阈值就是 2/3，一到就翻倍扩容并重新分配所有 key。这解释了为什么 get 平均只要 0.25 µs——它永远工作在 α ≤ 0.67 的舒适区里。

八、工程实现里的三个细节

1. Java HashMap：链 + 树 + 2 的幂

设计 做法 为什么
定位桶 (n - 1) & hash n 是 2 的幂时等价于 % n，但位运算快得多
扰动 h ^ (h >>> 16) 把高 16 位混进低 16 位，弥补「只取低位」
冲突 链表，长度 ≥ 8 且表长 ≥ 64 树化成红黑树 防哈希攻击/极端分布的 O(n) 退化
扩容 翻倍，元素要么在原位、要么原位+n 因为 n 是 2 的幂，重算下标只需看 hash 多出的那一位

2. 字符串哈希：31 的真相

Java String.hashCode() 用的是 s[0]·31^(n-1) + s[1]·31^(n-2) + … + s[n-1]。教材常说「31 是最好的基数」，理由是：

  • 31 是奇质数，与 2 的幂互质，能避免「低位全丢」；
  • 31·i == (i << 5) - i，可以用移位减法代替乘法，编译器/JIT 会自动这么优化。

但「最好」这个说法经不起实测。3 万个随机的 8 位小写串、桶数 10007：

结论有两层：

  • 31、33、37、131、26、1024 之间没有实质差别，最大桶长都在 11~13，落在随机波动的范围内。「31 最优」更像是「31 够用 + 有移位优化 + 历史沿用」，不是数学上的唯一正确答案。
  • 真正致命的是基数为 1：H = c0 + c1 + … + cn，只跟字符和（即字母的排列组合）有关，与顺序无关，3 万个串只落到 152 个桶、最大桶长 573。这类退化才是要防的，而不是纠结 31 还是 37。

3. 哈希攻击（HashDoS）

如果攻击者能构造大量同桶的 key，哈希表就退化成链表，单次请求的复杂度从 O(1) 变 O(n)——几个精心构造的 JSON 字段就能把服务打瘫。防御手段在各语言里都做成了默认行为：

  • Java：链表树化成红黑树，最坏 O(log n)
  • Python 3.3+：字符串哈希随机化（PYTHONHASHSEED），进程启动时加随机盐，攻击者没法离线构造碰撞
  • 各种 Web 框架：限制请求体里 key 的数量和长度

九、选型与三个必踩的坑

链地址 vs 开放定址怎么选

链地址 开放定址
α 上限 可 > 1 必须 < 1（通常 ≤ 0.7）
删除 摘链，干净 必须墓碑，且会积累
缓存友好度 差（跳指针） 好（连续内存）
额外空间 每元素一个指针 无指针，但表本身要留空位
大数据量 一般 通常更快（缓存命中率高）
典型实现 Java HashMap、Redis dict Python dict、Go map、ThreadLocalMap

小数据、删除频繁、α 不稳定 → 拉链；数据量大、追求常数、能控住 α → 开放定址。

坑 1：可变对象当 key

哈希表靠「哈希值找位置」，如果 key 存进去之后哈希值变了，就再也找不到它了。

  • Java：equals 和 hashCode 必须一起重写，且参与 equals 的字段不能变。用可变对象（如 ArrayList）当 HashMap 的 key，改完内容就成幽灵。
  • Python：list、dict、set 都不可哈希（unhashable type），tuple 可以，但 tuple 里塞了可变对象一样废。

坑 2：遍历顺序

哈希表的顺序是哈希值和实现细节决定的，不是插入顺序，也没有承诺稳定。

  • Java HashMap：不保证顺序；要顺序用 LinkedHashMap（插入序）或 TreeMap（key 排序）
  • Python dict：3.7 起保证插入序——但这是「compact dict」实现的副产品被写进了语言规范，不是哈希表的通性。把 Python 的习惯搬到 Java 会出 bug。

坑 3：「哈希表查找 O(1)」写成绝对结论

严格说是期望 O(1)，前提是均匀哈希 + α 受控。最坏情况是 O(n)：

  • 所有 key 撞进同一个桶（哈希函数退化成常数，或者被攻击）
  • α 逼近 1 的开放定址（实测 α=0.99 时线性探测要 19.58 次）

面试里答「哈希表平均 O(1)、最坏 O(n)、冲突用拉链或开放定址、开放定址删除要墓碑」，比只答「O(1)」完整得多。

十、小结

  • 哈希表把「按 key 找」变成「算地址直接跳」，O(n) → 期望 O(1)；代价是冲突不可避免（抽屉原理）。
  • 哈希函数要确定 + 均匀 + 快。除留余数法的 m 取质数是为了打散 key 的规律性；工程用 2 的幂是为了位运算快，代价是必须靠扰动补低位。
  • 装填因子 α 才是性能的自变量。实测 α 从 0.5 到 0.99：链地址 1.22→1.50 次，线性探测 1.38→19.58 次（最长连续块 756）。差 13 倍，靠的是冲突处理策略，不是哈希函数。
  • 链地址删除干净、α 可超 1，但缓存不友好；开放定址缓存友好、常数小，但必须留余量、删除必须打墓碑、墓碑会积累。
  • 工程实现都在用这两条：Python dict 的 α 阈值就是 2/3（实测在 5/10/21/42/85/170 个元素时扩容），Java HashMap 用 2 的幂 + 扰动 + 树化。
  • 「String 用 31 最好」实测没有压倒性优势（31/33/37/131 差别在噪声内），真正致命的是基数为 1 这类退化。别把经验口诀当定理。

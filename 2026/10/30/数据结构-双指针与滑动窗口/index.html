双指针与滑动窗口：省下的是复杂度，不是常数

双指针与滑动窗口：省下的是复杂度，不是常数

「双指针」这个词在题解里出现得太随意了。两数之和是两个指针，链表判环是两个指针，滑动窗口是两个指针，合并两个有序数组也是两个指针——但它们之间几乎没有共同点：移动规则不同，依赖的前提不同，正确性论证的方式也不同。

把它们笼统当成一个套路去背模板，结果就是遇到新题只能靠「这题看着像双指针」来猜。这篇文章想做的第一件事，是把这四种分工拆开，说清每一种凭什么是对的；第二件事，是用实测回答那个很少有人较真的问题——双指针到底快在哪，快多少。

剧透一下结论：它省下来的是复杂度阶，不是常数。有些场合（比如 Python 里的原地删除）手写双指针甚至比内置方法还慢，你要的其实是那个 O(1) 额外空间。

一、四种分工，先认清是哪一种

先看一张对照表。判断一道新题该用哪种，比背模板有用得多：

类型 两个指针的关系 移动规则 关键前提 典型题
对撞 一左一右，相向而行 根据比较结果决定动哪边 多数要求有序 两数之和 II、验证回文、盛水容器
快慢 同向，slow 是写指针、fast 是读指针 fast 每轮必动，slow 条件动 只需保持相对顺序 移除元素、去重、移动零
分离 各在一个数组上 谁小动谁，或各自独立推进 两个数组各自有序 合并有序数组、交集、长按键入
窗口 left 只追不超 right right 每轮必动，left 收缩 窗口条件必须有单调性 最长无重复、最短覆盖、定长子数组

骨架放在一起看，差异一目了然：

第一列（对撞）和第四列（窗口）看着都像「两个下标」，但性质完全不同：对撞的两个指针互相靠近，区间在缩小；窗口的 left 只追不超 right，区间在滑动。这个区别决定了它们能解决的问题类型完全不同。

二、对撞指针：有序才是它敢跳的前提

对撞指针最容易被误用成「只要写两个下标就行」。它的核心其实是一个排除论证：当我知道当前的 nums[lo] + nums[hi] 太小，我凭什么敢把 lo 整个排除掉？

答案是有序。若数组升序、且 nums[lo] + nums[hi] < target，那么对于所有 j ≤ hi，都有 nums[lo] + nums[j] ≤ nums[lo] + nums[hi] < target。也就是说 nums[lo] 配谁都凑不到目标，可以放心丢掉。

这段推理里「升序」是不可省的。把同样的代码扔到无序数组上，它不会报错，只会悄悄给出错误答案——这是对撞指针最阴险的地方：错得没有声音。

我拿 3000 组随机小数组做过存在性对比，有序前提下与暴力完全一致（0 例不符）；一旦打乱顺序，它就开始随机漏解。

三、同一个对撞，两种不同的正确性依据

有意思的是，并非所有对撞指针都靠有序。盛最多水的容器就是反例：柱子高度任意打乱，标准解法照样对。

这里的依据换成了另一句话：面积由矮的那根决定，挪走高的一根只会让宽度变小、高度不增，必然不优。所以每次挪矮的，一定不会错过最优解。整套论证和「有序」没有半点关系。

所以判断一道题能不能用对撞，真正要问的不是「数组有序吗」，而是「我有没有一个理由，能安全地扔掉一端」。有序是这种理由中最常见的一个，但不是唯一的。

两数之和 II 盛最多水的容器
移动依据 和太小 / 太大 哪边矮
正确性来源 数组有序 ⇒ 可排除整端 短板决定上限 ⇒ 挪高柱无益
需要有序吗 需要 不需要
移动后的区间 仍是候选解的全集 仍包含最优解

四、快慢指针：slow 是写指针，fast 是读指针

快慢指针换个说法就好懂了：fast 负责读，slow 负责写。slow 左边的区域永远「已经处理干净」，fast 挨个把要保留的元素搬到 slow 的位置上。

这个模型一立起来，「为什么它能保持相对顺序」也就自然了：元素是按 fast 的遍历顺序被搬过去的，先后关系没变。对比下面这种交换式的写法（把后面的元素换到前面），虽然也 O(n)，但顺序会乱——题目若要求保序就不能用。

那么它快吗？在 C 里当然快，O(1) 额外空间、零分配。但在 Python 里，实测结果有点扫兴（n 个随机 1~5 的整数，删掉所有的 3，单位 ms）：

元素数 n 保留元素 快慢指针 反向 pop 列表推导式重建
20,000 16,001 1.20 0.51 0.60
100,000 80,061 5.95 2.67 3.71
400,000 319,361 23.64 10.62 17.41

三种实现结果完全一致（逐个元素核对过），但手写的快慢指针是最慢的，比反向 pop 慢 2.2 到 2.4 倍。

原因不复杂：快慢指针是逐元素的 Python 循环，每次都要走一遍字节码；而 list.pop 和列表推导式的循环发生在 C 层。省下的那点内存访问，抵不过解释器的开销。

所以快慢指针在 Python 里的价值不是「更快」，而是三件事：一是 O(1) 额外空间（大数组时这真的重要）；二是它是流式的，数据一个个来也能处理，不必先攒成列表；三是这个模型能直接搬到链表上，而链表根本没有 pop 可用。

五、链表上的 Floyd：为什么相遇点能反推入口

链表判环是快慢指针最经典的应用。slow 每轮走一步，fast 每轮走两步，如果存在环，fast 一定会在环内追上 slow。

第二段的推导值得记一遍。设头到环入口距离为 a，入口到相遇点距离为 b，环长为 L。相遇时 slow 走了 a + b，fast 走了 a + b + kL，而 fast 的路程是 slow 的两倍，所以 a + b = kL，即 a = kL - b。这意味着从头走 a 步，与从相遇点走 (L−b) 步，会同时到达入口——这就是「一个指针回起点、两人同速再走」能对上入口的原因。

实测一条 100 万个结点的链、环入口在第 700,000 个结点（环长 300,000）：

  • 判环耗时 37.5 ms
  • 找环入口耗时 53.7 ms，返回的结点值正是 700000
  • 1000001 个结点找中点耗时 17.5 ms，返回第 500000 个结点

顺手验证了一个有意思的量：判环时快慢相遇用了 900,000 轮。按上面的记号，应该是 a + (L − a mod L) = 700000 + (300000 − 100000) = 900000，完全吻合。这个数字说明相遇发生在环内绕了快一圈之后，而不是一进环就撞上——这也是为什么不能靠「进环就相遇」来简化实现。

六、分离双指针：从后往前填，才不会互相踩

合并两个有序数组是分离双指针的入门题。真正的坑在 LeetCode 88 那种输入形态：nums1 已经预留了后半段空间，要求原地合并。如果从前往后填，会覆盖掉还没处理的元素。

关键只有一个：从后往前填，写入位置永远在未读元素之后，所以绝不会踩到还没读的值。

循环条件写成 while j >= 0 而不是 while i >= 0 and j >= 0，是因为 b 一旦填完，a 剩下的部分本来就在正确位置上，不用管。

效率上我原本以为后插法会明显更快（毕竟省了一次完整拷贝），实测却几乎打平（两个长度 n 的有序数组，单位 ms）：

数组长度 n 前插新建 res 后插原地（已预留空间） 比值
50,000 6.47 6.47 1.00
200,000 33.78 29.24 1.16
800,000 252.57 225.37 1.12

只快 0 到 16%。原因还是那个：Python 的 append 均摊 O(1)，本来就便宜，省下的一次分配在总时间里的占比很小。

这个优化在 C 或 Java 里价值大得多——那边省掉的是一整次 O(n) 内存拷贝和一块临时空间。同一个技巧在不同语言里的收益差一个数量级，这类判断最好都实测一下再下结论。

七、定长窗口：把 sum() 换成增量

窗口长度固定为 k 时，最直白的写法是每个窗口重新求和。它没错，但复杂度是 O(nk)。滑动窗口的全部意义就是把「重新算一遍」换成「加进来的减出去的」：

两者结果逐项校验过，完全一致。性能差距取决于 k 有多大（n 个 -100~100 的随机整数，单位 ms）：

n k 每窗 sum() 增量维护 比值
20,000 100 23.47 1.73 13.6
20,000 1,000 259.76 1.84 141.3
100,000 50 75.15 8.89 8.5
100,000 5,000 8057.42 8.20 983.1

把表读成一句话：增量维护的耗时几乎不随 k 变，而每窗重算的耗时正比于 k。n=100,000、k=5,000 时差了 983 倍，8 秒对 8 毫秒。

顺带说一个 Python 特有的坑：cur += nums[i] - nums[i-k] 这种写法是安全的，但如果窗口内的量不支持减法（比如要求最大值），就没法用增量了——那时要换数据结构，见第九节的单调队列。

八、变长窗口：收缩必须用 while

定长窗口的 left 是被 right 推着走的，一进一出，节奏固定。变长窗口的 left 得自己追，而且必须一直追到条件被破坏为止。这一步写成 if 是最常见、也最致命的错误：

写错的样子长这样——把 while 换成 if，每轮只缩一次：

这版在两个小例子上就露馅了：

  • nums = [2,3,1,2,4,3]，target = 7：正确答案 2（[4,3]），if 版给出 4
  • nums = [1,4,4]，target = 4：正确答案 1，if 版给出 2

放到 20,000 组随机用例上跑，if 版错了 7,480 组（37.4%），而 while 版在 5,000 组里 0 错。最小反例是 nums = [4,6,9,3,8,9]、target = 13：正确答案 2（[4,9]），if 版给 3。

根本原因：右指针加入一个元素后，可能让条件超额满足（比如一下子进来一个大数），此时缩一步还不够，得连缩好几步才能逼近最短。用 if 等于假设「每次最多超一格」，这个假设不成立。

能这么写的底气在均摊分析：left 从头到尾只增不减，最多走 n 步，所以内层 while 虽然看着嵌套，总代价仍是 O(n)。嵌套层数不等于复杂度。

九、滑动窗口能不能用，只看一条：单调性

窗口类的题，判据只有一个：加入元素后条件变难满足、移除元素后条件变容易满足。有这条单调性，left 才不会来回摇摆，才能「只追不超」。

换句话说，如果一道题的约束是「窗口里恰好有 2 个奇数」，那它就不是滑动窗口能处理的——多进来一个奇数后，你不确定该扔哪边。这时候该上哈希表或前缀和。

用最长无重复子串做个实验，能看到一个反直觉的现象：暴力解与窗口解的差距不是固定的。

输入 n 暴力 O(n²) 窗口 O(n) 比值
只有 7 种字符 500 0.14 0.042 3.2
只有 7 种字符 4,000 1.03 0.342 3.0
字符全不相同 500 11.65 0.047 249.9
字符全不相同 1,000 44.95 0.093 485.4
字符全不相同 2,000 198.23 0.191 1035.2
字符全不相同 4,000 817.82 0.440 1859.1

字符集只有 7 个时，暴力版的内层循环很快就撞到重复、break 出来，实际跑的是近似线性——所以差距只有 3 倍。字符全不相同时，内层永远不 break，暴力才真正退化成 O(n²)：n 翻倍时间涨 4 倍，差距从 250 倍涨到 1859 倍。

这提醒一件事：复杂度分析给的是渐近趋势，具体快多少要看输入。说「滑动窗口比暴力快 O(n)」没错，但如果你手上的输入字符集很小，优化收益可能只有 3 倍，把代码改复杂并不划算。

窗口里还常需要维护最值，这时增量法用不了（最大值没法「减出去」），得请出单调队列：

它和「每个窗口 max() 扫一遍」的对比（n 个 1~1,000,000 的随机整数，单位 ms）：

n k 每窗 max() 单调队列 比值
20,000 100 26.91 4.89 5.5
20,000 2,000 480.85 5.03 95.5
100,000 500 659.13 27.98 23.6

单调队列的每个下标最多被压入一次、弹出一次，所以整体 O(n)——它和第七节的增量法是同一个思路：别重算，只维护变化。

十、五个坑，和一句小结

一、对撞的循环条件用 < 还是 <=。 取决于是否允许同一个元素用两次。两数之和要求两个不同下标，写 lo < hi；如果允许自身配对（比如判断回文允许中心点），写 lo <= hi。写反了不会崩，只会多算或少算一个。

二、三数之和的去重要在三个位置都做。 固定第一个数时跳重复、lo 命中后跳重复、hi 命中后跳重复，漏一个就会出重复三元组。这也是为什么三数之和的代码看着比两数之和长一倍多——一半篇幅在去重。

三、窗口收缩写 if 不写 while。 上面已经用 7,480 组反例说明过了，这是四个错误里唯一会大面积错的。

四、定长窗口里 left 和 right 的联动别写乱。 长度到达 k 之后，每轮应该是「先更新答案，再出队一格、left 加一」，顺序反过来就少算最后一个窗口。

五、快慢指针里 fast.next 要判两次。 while fast and fast.next 两个条件缺一不可：fast 为空说明走到链表尾，fast.next 为空说明下一步的 fast.next.next 会炸。只判一个，长度偶数或长度为 1 的链表必崩。

回到开头那个问题：双指针值不值得学？值得，但值得的地方是复杂度，不是常数。最坏情况下两数之和的暴力解与对撞解差 2,483 倍（n=8,000：794.89 ms 对 0.32 ms），盛水容器差 8,510 倍（n=20,000），这是数量级的碾压，任何常数优化都追不回来。但在移除元素这类题上，Python 的手写双指针比内置 pop 慢 2.3 倍，你换到的是 O(1) 空间和流式处理能力。

分清这两件事，才不会把「用了双指针」当成「写得更快」的同义词。

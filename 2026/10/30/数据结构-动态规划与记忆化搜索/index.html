动态规划与记忆化搜索：同一个状态，两种走法

「动态规划」这四个字最容易把人劝退的地方，是它听起来像一个需要从头搭起的理论体系。但它要解决的问题其实朴素得过分：同一个小问题被反复计算了很多次，把答案记下来别重算。

这句话说起来像常识，可一旦落到代码上，会有两个完全不同的走法——顺着递归往下想，算出答案就记进备忘录；或者倒过来，先算小的再推大的。这两个走法算的是同一张表，只是填表顺序相反。

这篇文章想把这两条路都走一遍，并且用实测回答三个问题：记忆化到底省了多少、它省不了什么、什么时候必须换成自底向上。

一、先分清三个词：递归、记忆化、动态规划

这三个词经常被混着用，其实是一条清晰的递进关系：

概念 角色 一句话
递归 骨架 把大问题拆成同构的小问题，自顶向下
记忆化 优化手段 给递归挂一个备忘录，重复的状态直接查表
动态规划 最终形态 可以是「带缓存的递归」，也可以是「自底向上的循环」

用等式写就是：动态规划 = 递归 + 记忆化，或者动态规划 = 状态定义 + 转移方程 + 遍历顺序。前一个式子讲的是「怎么想到」，后一个讲的是「怎么写出来」。

分清这一点有实际好处：拿到一道题，先顺直觉写递归（这一步谁都会），再看递归树里有没有重复状态。有，就加备忘录；加完发现递归太深或者状态转移很适合循环，就改写成迭代。不要一上来就想转移方程——那是把最难的步骤放在了最前面。

二、爆炸从哪里来：fib(30) 的 269 万次调用

斐波那契是最小可用的例子，因为它把「重复」这件事暴露得特别干净：

fib(5) 会算 fib(3) 两次，fib(30) 会算 fib(28) 两次、fib(27) 三次……重复量呈指数增长。我在递归入口加了计数器，实测调用次数：

n fib(n) 函数调用次数 状态其实只有
10 55 177 11 个
15 610 1,973 16 个
20 6,765 21,891 21 个
25 75,025 242,785 26 个
28 317,811 1,028,457 29 个
30 832,040 2,692,537 31 个

两列一比就清楚了：答案只需要 31 个状态，程序却做了 269 万次计算。多出来的 269 万次，全是把同一件事重做了一遍。记忆化要做的，就是让这 269 万次变成查表。

顺带一个常被忽略的事实：这 269 万次里绝大多数发生在树的底层。fib(2) 被算了上百万次，fib(29) 只算了一次。所以缓存对「靠近叶子」的状态收益最大——这也是为什么记忆化的效果比直觉上更夸张。

三、记忆化就是给递归挂个备忘录

记忆化的代码结构几乎是固定的三段：查表、算、存表。

三段的顺序不能乱。查表必须放在最前面，否则等于没缓存；存表必须在 return 之前，否则这次算的结果丢了。

四、同一件事，自底向上再写一遍

自底向上把「递归」换成「循环」，从最小的状态开始填表：

看着比递归「不像人话」，但它有两个递归拿不到的好处：没有函数调用开销，不受递归深度限制。对 fib 这种一维、只依赖前两项的状态，迭代版还能顺手把空间压到 O(1)。

这两种写法不是二选一的关系。实践中的顺序通常是：先用记忆化把题做对，再视需要改写成迭代。因为改写的难点从来不是循环，而是「状态依赖谁」——而这个问题在递归版里已经写明白了。

四步里最容易做错的是 Step 1。方程、初始化、顺序都是机械动作，唯独「dp[i] 到底代表什么」一旦定义错，后面全盘皆错——而且报错方式是「答案不对」，不是「代码崩了」。

五、四步法：状态、方程、初始化、顺序

把上一节的注释抽出来，就是一张通用检查表：

步骤 要做的事 判断标准 常见错法
1 定义状态 dp[i] / dp[i][j] 的含义 能用一句话说清，且能覆盖所有情况 漏掉一个维度（见第九节）
2 推导方程 当前状态由哪些旧状态推出 每种决策都要出现在 max/min/求和里 漏掉「不选」这一支
3 初始化 边界状态的答案 边界要能被方程自然消费 下标 0 与 1 混用
4 确定顺序 按什么方向遍历 计算 dp[i] 时依赖项必须已算好 一维背包写成从小到大（变成完全背包）

六、什么题能做 DP：三个判据

不是所有「能拆成子问题」的题都能 DP。三个条件缺一不可：

最优子结构：大问题的最优解由子问题的最优解拼成。最短路径满足（去终点的最短路必经中途某点的最短路），但「最长简单路径」不满足——子问题的最优解拼起来可能成环。

重叠子问题：递归树里同一个状态出现多次。没有重叠就退化成普通分治，缓存也没用——归并排序的子问题互不重叠，加备忘录纯属浪费内存。

无后效性：一旦状态确定，后面的决策不再关心「是怎么走到这个状态的」。这条最容易被违反，而且违反了通常看不出来。

我构造过一个最小的反例：爬楼梯，但限制「最多只能迈 6 步」。如果状态只记「当前在第几阶」，答案是 89；正确约束下只有 16 种。差别在于「已用步数」这个信息被丢掉了——它影响后续能不能继续走，所以它必须进状态。

n=10、上限 6 步时，前者给 89、后者给 16；把上限放宽到 10 步，两者又都回到 89。这个对照说明：错的不是公式，是状态定义漏了维度。

七、实测：三种写法的真实差距

同样算 fib，四种写法在同一台机器上的耗时（单位 ms，三次取最优）：

n 朴素递归 dict 备忘录 lru_cache 迭代（O(1) 空间）
20 1.121 0.0024 0.0044 0.0004
25 12.444 0.0029 0.0050 0.0005
28 50.959 0.0033 0.0054 0.0005
30 135.611 0.0036 0.0055 0.0005

三个结论，一个比一个反直觉：

第一，记忆化的收益是断崖式的。 n=30 时朴素递归 135.6 ms，记忆化 0.0036 ms，差 3.8 万倍。这不是「优化」，这是换了一个算法。

第二，lru_cache 比手写 dict 慢。 0.0055 vs 0.0036，慢约 50%。因为装饰器版本多了一层包装函数和 LRU 链表维护。n=900 时是 0.2014 vs 0.1646，慢 22%。差异不大，但方向一致——对性能敏感时手写 dict 更实在。

第三，迭代永远最快。 n=900 时迭代 0.0186 ms，记忆化 0.1646 ms，差 8.9 倍。因为记忆化要付两笔额外开销：函数调用和字典查找，而迭代两样都不用付。

不过这不意味着记忆化没价值。看背包问题的数据（物品价值与重量随机，容量固定，单位 ms）：

物品数 容量 朴素递归 记忆化 迭代 DP
10 50 0.138 0.052 0.017
14 80 2.122 0.117 0.038
18 100 35.950 0.217 0.064

物品数从 10 涨到 18，朴素递归从 0.138 涨到 35.950（261 倍），而记忆化只从 0.052 涨到 0.217（4 倍）。记忆化的斜率跟状态数走，不跟递归树走——这正是它该有的样子。

八、空间优化：滚动数组与维度压平

记忆化的空间复杂度是「状态数」，这对二维以上的问题很致命。编辑距离就是个典型：m × n 张表。

但注意到一个事实：算 dp[i][j] 只用到 dp[i-1][j]、dp[i][j-1]、dp[i-1][j-1]——只有上一行和本行。所以整张表可以压成两行：

实测两个长度相同的随机串（值域只有 4 个字符，所以内存数字就是数组本身的开销）：

长度 状态数 整表内存 两行内存 整表耗时 两行耗时
200 40,000 0.30 MB 0.00 MB 3.9 ms 2.7 ms
500 250,000 3.5 MB 0.03 MB 383.7 ms 209.7 ms
1,000 1,000,000 26.6 MB 0.07 MB 2,938.8 ms 2,813.8 ms
2,000 4,000,000 118.1 MB 0.14 MB 24,575.5 ms 13,127.8 ms

两个发现：一是内存从 118 MB 压到 0.14 MB，843 倍；二是时间也快了一倍——不是算法变了，而是整表那版要反复分配 2000 个列表，缓存局部性差，Python 的分配器被拖垮了。

空间优化有时候顺带把时间也优化了，这在 Python 里比在 C 里更明显。

顺带说一个 Python 特有的坑：我一开始想用爬楼梯演示滚动数组的内存收益，结果 n=400,000 时整表峰值测出 6.9 GB。那不是数组的锅——fib(400000) 本身有 8 万多位数，每个 dp 元素都是一个巨型整数。测内存要选值域有界的 DP（编辑距离、背包这类），否则测的是大整数的开销。

九、记忆化的两个硬边界

记忆化把时间从指数降到线性，但它绕不过两件事。

第一件：递归深度。 Python 默认上限 1000 层，记忆化不改这个事实。实测（上限设回默认值）：

  • n=300、n=900：递归版成功
  • n=1200、n=3000：递归版抛 RecursionError，迭代版照样成功

1200 这个数字值得记住——它比很多人预估的「几万」小得多。一条长度为 1200 的链，递归深度就是 1200。只要状态数可能上千，记忆化就必须改写成迭代，或者显式调高 sys.setrecursionlimit（同时要确认栈真的够用，否则从 RecursionError 变成段错误）。

第二件：状态必须可哈希且完整。 memo 的 key 通常是元组，这要求状态里的每一部分都是不可变且可 hash 的。如果状态里含列表或字典，就得先转成元组；如果状态漏了维度，缓存就会跨语境命中错误的结果——这类 bug 比没缓存更难查，因为「有时对、有时不对」。

十、五个坑与小结

一、dp 的定义说不清就别写代码。 一句话讲不出「dp[i] 是什么」，说明状态还没想清。这一步花的十分钟，能省掉后面一小时的调试。

二、一维背包的正序与倒序。 倒序是 0/1（每件一次），正序是完全背包（无限次）。写反不报错，答案偏大。

三、初始化要能被方程消费。 dp[0] 到底该是 0 还是 1，取决于「空集算不算一种方案」。爬楼梯 dp[0]=1（不动也是一种走法），最大子序和则不能这么设——同一个 0 在不同题里含义不同。

四、lru_cache 的缓存跨调用存活。 写在模块级函数上，多次测试会命中旧缓存。要么每轮重建函数，要么 cache_clear()。

五、别用递归写状态数可能上千的 DP。 迭代不是「更优雅」，是「唯一能跑」。

最后回到那个等式。动态规划之所以让人觉得难，是因为教科书写的是后半句（状态、方程、顺序），而人脑顺着想的是前半句（递归、然后缓存）。从递归起步不是偷懒，是顺着认知顺序走：先让代码正确，再让它不重复，最后才考虑让它更快、更省。

真要记一句话的话，记这句：当你的递归树里同一个节点出现了第二次，你就已经站在动态规划的门口了。

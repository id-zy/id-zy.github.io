# 262. 行程和用户

> **难度**：困难 | **题号**：262 | **链接**：[262. 行程和用户 - 力扣（LeetCode）](https://leetcode.cn/problems/trips-and-users/) | **数据结构**：SQL
>
> 关联：每月交易 I（同为「条件聚合」求比率，那题用 `SUM(state='approved')`）· 电影评分（多表联查 + 排序取首）· 查询近30天活跃用户数（日期区间过滤）· 上升的温度（日期比较）· 分数排名（窗口函数替代方案）。

## 🎯 问题描述

**描述**：`Trips` 表存放了所有出租车的行程信息，`Users` 表存放了所有用户信息（乘客与司机共存，靠 `role` 区分）。写一段 SQL 查询，查出 **2013-10-01 至 2013-10-03** 期间**非禁止用户**（乘客和司机都未被封禁）的**取消率**，结果保留 **两位小数**。

> 取消率的定义：**被司机或乘客取消的非禁止用户行程数** ÷ **非禁止用户的总行程数**。
> 「非禁止用户」= 该行程的 `client_id` 和 `driver_id` 都对应 `Users.banned = 'No'`。

**表：Trips**

```text
+-------------+----------+
| Column Name | Type     |
+-------------+----------+
| id          | int      |
| client_id   | int      |
| driver_id   | int      |
| city_id     | int      |
| status      | enum     |
| request_at  | date     |
+-------------+----------+
id 是这张表的主键（具有唯一值的列）。
这张表中存所有出租车的行程信息。每段行程有唯一 id，其中 client_id 和 driver_id 是 Users 表中 users_id 的外键。
status 是一个表示行程状态的枚举类型，枚举成员为 ('completed', 'cancelled_by_driver', 'cancelled_by_client')。
```

**表：Users**

```text
+-------------+----------+
| Column Name | Type     |
+-------------+----------+
| users_id    | int      |
| banned      | enum     |
| role        | enum     |
+-------------+----------+
users_id 是这张表的主键（具有唯一值的列）。
这张表中存所有用户，每个用户都有一个唯一的 users_id。
banned 是一个表示用户是否被禁止的枚举类型，枚举成员为 ('Yes', 'No')。
role 是一个表示用户角色的枚举类型，枚举成员为 ('client', 'driver', 'partner')。
```

**示例 1**：

```text
输入：
Trips 表：
+----+-----------+-----------+---------+---------------------+------------+
| id | client_id | driver_id | city_id | status              | request_at |
+----+-----------+-----------+---------+---------------------+------------+
| 1  | 1         | 10        | 1       | completed           | 2013-10-01 |
| 2  | 2         | 11        | 1       | cancelled_by_driver | 2013-10-01 |
| 3  | 3         | 12        | 6       | completed           | 2013-10-01 |
| 4  | 4         | 13        | 6       | cancelled_by_client | 2013-10-01 |
| 5  | 1         | 10        | 1       | completed           | 2013-10-02 |
| 6  | 2         | 11        | 6       | completed           | 2013-10-02 |
| 7  | 3         | 12        | 6       | completed           | 2013-10-02 |
| 8  | 2         | 12        | 12      | completed           | 2013-10-03 |
| 9  | 3         | 10        | 12      | completed           | 2013-10-03 |
| 10 | 4         | 13        | 12      | cancelled_by_driver | 2013-10-03 |
+----+-----------+-----------+---------+---------------------+------------+
Users 表：
+----------+--------+--------+
| users_id | banned | role   |
+----------+--------+--------+
| 1        | No     | client |
| 2        | Yes    | client |
| 3        | No     | client |
| 4        | No     | client |
| 10       | No     | driver |
| 11       | No     | driver |
| 12       | No     | driver |
| 13       | No     | driver |
+----------+--------+--------+
输出：
+------------+-------------------+
| Day        | Cancellation Rate |
+------------+-------------------+
| 2013-10-01 | 0.33              |
| 2013-10-02 | 0.00              |
| 2013-10-03 | 0.50              |
+------------+-------------------+
解释：
2013-10-01：非禁止用户共 3 段行程（id 1、3、4），其中 id 4 被取消 → 1/3 = 0.33。
  注：id 2 的乘客是 users_id = 2（banned = Yes），整段行程被排除。
2013-10-02：非禁止用户共 2 段行程（id 5、7），无取消 → 0/2 = 0.00。
  注：id 6 的乘客是 users_id = 2（banned = Yes），被排除。
2013-10-03：非禁止用户共 2 段行程（id 9、10），其中 id 10 被取消 → 1/2 = 0.50。
  注：id 8 的乘客是 users_id = 2（banned = Yes），被排除。
```

**提示**：

- **乘客和司机要各查一次 `Users`** —— 两个 `JOIN Users`，必须起别名区分（`c` / `d`），并且**两个 `banned = 'No'` 都要加**。
- **分母是「过滤后的行程数」** —— 如果先算比率再过滤，或过滤条件写在 `HAVING` 外，分母就会被污染。
- 取消 = `status != 'completed'`（含 `cancelled_by_driver` 与 `cancelled_by_client` 两种），不必枚举。
- 结果列名要带反引号：`Day`、`Cancellation Rate`（含空格，必须引起来）。
- 日期是 `date` 类型，`BETWEEN '2013-10-01' AND '2013-10-03'` **包含两端**。

## 💻 解题思路

### 思路 1：两次 JOIN 过滤 + SUM(IF) 条件聚合（用户解法）

#### 核心逻辑

① 用 `JOIN Users c` 和 `JOIN Users d` 把乘客、司机的 `banned` 拉进来（**内连接**顺带保证了「用户存在」）；② `WHERE` 里同时过滤日期与两个 `banned = 'No'`，此时表里只剩「非禁止用户的有效行程」；③ 按日期分组，分子用 `SUM(IF(status != 'completed', 1, 0))`、分母用 `COUNT(*)`；④ `ROUND(..., 2)` 保留两位。

#### 代码实现

```sql
# Write your MySQL query statement below
SELECT
    t.request_at AS `Day`,
    ROUND(
        SUM(IF(t.status != 'completed', 1, 0))
        / COUNT(*),
        2
    ) AS `Cancellation Rate`
FROM Trips t
JOIN Users c ON t.client_id = c.users_id
JOIN Users d ON t.driver_id = d.users_id
WHERE
    t.request_at BETWEEN '2013-10-01' AND '2013-10-03'
    AND c.banned = 'No'
    AND d.banned = 'No'
GROUP BY t.request_at;
```

#### 📊 性能分析

- 时间复杂度：$O(n + n \log n)$，$n$ = `Trips` 行数（两次索引查找连接 + 分组排序）。
- 空间复杂度：$O(d)$，$d$ = 涉及日期数（分组结果极小）。
- 索引建议：`Users(users_id)` 是主键直接命中；`Trips(request_at)` 建索引可把日期过滤提前，避免全表连接。

#### 思考

- **`SUM(IF(...))` 的三种等价写法**（都值得会）：
  | 写法 | 说明 |
  |---|---|
  | `SUM(IF(status != 'completed', 1, 0))` | 最直白，跨库可移植（Oracle 用 `DECODE`/`CASE`） |
  | `SUM(status != 'completed')` | MySQL 里布尔即 0/1，最短；依赖方言 |
  | `AVG(status != 'completed')` | 平均值就是比率，**省掉分母**，且天然除以"过滤后的行数" |
  | `SUM(CASE WHEN status != 'completed' THEN 1 ELSE 0 END)` | SQL 标准写法，可移植性最好 |
- **`COUNT(*)` 作为分母是安全的**：因为 `users_id` 是 `Users` 的主键，两次内连接都是 **1:1**，不会把行数放大。若 `Users` 里出现重复 `users_id`（脏数据），比率会被悄悄放大 —— 面试可主动提这一点。
- **`WHERE` 与 `HAVING` 的位置**：`banned` 是行级条件，必须放 `WHERE`（先过滤再聚合），分子分母才一致。若放到 `HAVING` 就是"先按含禁止用户的行算比率、再筛组"，结果全错。
- **日期区间**：`BETWEEN` 对 `date` 含两端；若字段是 `datetime`（带时分秒），`BETWEEN '2013-10-01' AND '2013-10-03'` 会漏掉 10-03 当天 00:00:00 之后的数据 —— 更稳的写法是 `>= '2013-10-01' AND < '2013-10-04'`（左闭右开，与 查询近30天活跃用户数 同一心法）。
- **没有行程的日期不会出现在结果里**：`GROUP BY` 只对存在的行分组，题目的示例恰好每天都有有效行程。若要求"空日补 0"，就得像 学生们参加各科测试的次数 那样先造日期骨架再 `LEFT JOIN`。
- **`ROUND` 不是 `TRUNCATE`**：题面要四舍五入，`TRUNCATE(x, 2)` 会截断导致 0.335 → 0.33（应为 0.34）。另外 `ROUND` 返回的是 `decimal`，LeetCode 判题按数值比，格式无碍。

### 思路 2：AVG 一行流（最简写法）

#### 核心逻辑

比率的本质就是**布尔值的平均**。既然 `WHERE` 已经把无关行程全部剔除，直接对 `status != 'completed'` 求 `AVG` 即得取消率，不写分子分母。

#### 代码实现

```sql
SELECT
    t.request_at AS `Day`,
    ROUND(AVG(t.status != 'completed'), 2) AS `Cancellation Rate`
FROM Trips t
JOIN Users c ON t.client_id = c.users_id AND c.banned = 'No'
JOIN Users d ON t.driver_id = d.users_id AND d.banned = 'No'
WHERE t.request_at >= '2013-10-01'
  AND t.request_at <  '2013-10-04'
GROUP BY t.request_at
ORDER BY t.request_at;
```

#### 📊 性能分析

- 时间复杂度：$O(n \log n)$，与思路 1 同阶（少了两次常量加法，常数项略优）。
- 空间复杂度：$O(d)$。
- 注意 `banned = 'No'` 放进了 `ON` 而不是 `WHERE`：**这里是内连接，两者等价**；一旦改成 `LEFT JOIN`（比如要保留"乘客不存在"的行程）语义就完全不同 —— 放 `ON` 不会过滤行程，放 `WHERE` 会。这个区别是本类题的高频追问。

#### 思考

- `AVG(布尔)` 的优势是**不用关心"分母该数谁"**，天然避免"分子分母用了不同过滤条件"这类错。
- 加 `ORDER BY` 更稳：题面虽未强制排序，但判题通常期望按日期升序（MySQL 8 不保证 `GROUP BY` 的输出顺序）。

## 📝 总结

「**按维度求比率（取消率 / 通过率 / 转化率）**」的固定套路：

1. **先把口径过滤干净**（行级条件全放 `WHERE` / `ON`），确保分子分母同一批行；
2. **条件聚合求分子**：`SUM(IF(cond,1,0))` / `SUM(cond)` / `SUM(CASE WHEN …)`；
3. **分母用 `COUNT(*)` 或干脆用 `AVG(cond)` 省掉分母**；
4. `ROUND(x, 2)` 保留两位，别用 `TRUNCATE`。

核心坑点：① 乘客、司机要**各查一次 `Users`**，漏一个就错；② `banned` 过滤放在聚合之后 → 分子分母口径不一致；③ `COUNT(*)` 依赖连接是 1:1（主键连接才安全）；④ `date` 与 `datetime` 的区间边界差异（左闭右开最稳）；⑤ 列名含空格必须加反引号。

> 一句话：**比率题的分水岭不在公式，在"分母是谁"** —— 口径一歪，算得再准都是错的。

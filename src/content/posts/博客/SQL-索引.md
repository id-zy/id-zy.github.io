# SQL 索引：为什么加了索引还是慢，回表与最左前缀

很多人给字段加了索引，查询却没变快，甚至 `SELECT *` 一上来就绕开索引走全表。问题往往不在「加没加索引」，而在「知不知道索引在底层长什么样」。这篇把 B+ 树、聚簇索引、回表、覆盖索引、最左前缀串成一条线，讲清它们之间的因果关系。

## 一、B+ 树：为什么索引的数据结构是它

数据库索引选 B+ 树，不是因为它叫「树」，而是它的几个结构特点恰好命中磁盘和范围查询的痛点：

- **非叶子节点只存键和指针**，不存完整数据。
- **所有数据都在叶子节点**。
- 叶子节点按 key 有序，并用**双向链表**串起来。
- 树很矮，通常 3～4 层就能存千万到亿级数据。

为什么这些特点重要？磁盘 IO 是数据库查询最贵的成本，而一次查询要访问的页数由「树高」决定。非叶子节点不存数据，意味着一个 16KB 的页能塞进更多 key，树就更矮，查询要翻的页就更少。

B+ 树和 B 树最核心的区别就一句：**B+ 树数据全在叶子、非叶子只存 key，且叶子用链表串起来**。这带来两个直接好处：① 非叶子能放更多 key，树更矮，磁盘 IO 更少；② 叶子链表让范围查询顺着扫就行，不用回溯。所以 InnoDB 选 B+ 树而不是 B 树。

## 二、聚簇索引与回表：主键快、二级慢的根因

「主键索引就是聚簇索引」，它的叶子节点存的是**主键值 + 整行数据**。也就是说，表数据本身就是按主键顺序组织的一棵 B+ 树。

如果建表时没指定主键，InnoDB 会依次尝试：选第一个非空唯一索引当聚簇索引；再没有，就生成隐藏的 `row_id`。

聚簇索引让主键查询、主键范围查询、按主键排序都很快，但它也有约束：主键不能太长（否则所有二级索引都会跟着变大），随机主键（比如 UUID）容易造成页分裂，所以一般建议用**短、自增、有序**的主键。

而二级索引（辅助索引、非聚簇索引）的叶子节点，存的是**索引列的值 + 主键值**，不存整行。于是有了「回表」：

```sql
-- 假设 user 表只有主键 id 和二级索引 idx_name(name)
SELECT * FROM user WHERE name = 'Alice';
```

执行过程是这样的：

```text
① 走二级索引 idx_name，找到 (Alice, 1/3/6) 三个主键值
② 拿这三个主键，逐个回聚簇索引查整行
```

代价是 1 次二级索引查找 + 3 次聚簇索引查找，而且这 3 个 id 可能分散在不同页，产生随机 IO。

判断会不会回表，就看 `SELECT` 要的列是不是都在二级索引里——都在就不用回表，缺了就要拿主键回聚簇索引取整行。所以 `SELECT *` 几乎必然回表。

实测（MySQL 8.0.12）这条回表查询的 `EXPLAIN`，关键看 `Extra` 是空的：

```text
type=ref | key=idx_name | key_len=83 | Extra=NULL
```

`Extra` 为空（不是 `Using index`），就是「要回表取整行」的信号——这也是下一节覆盖索引要解决的痛点。

## 三、覆盖索引：不回表的捷径

如果一条查询需要的所有列都能从索引里直接拿到，就不需要回表，这叫**覆盖索引**。`EXPLAIN` 里看到 `Extra: Using index`，就是这种情况。

```sql
SELECT id, name FROM user WHERE name = 'Alice';
-- idx_name 的叶子存 (name, id)，id 和 name 都在里面
-- 直接返回，不回表
```

实测（MySQL 8.0.12，`EXPLAIN` 看 `Extra`）两条命令的差别：

```text
SELECT *         → Extra: NULL          （要回表）
SELECT id, name  → Extra: Using index   （覆盖，不回表）
```

覆盖索引是减少回表、提升性能的重要手段，但要注意 `SELECT *` 通常无法覆盖，因为索引里一般没有所有列。

## 四、最左前缀：联合索引的排序铁律

联合索引 `(a, b, c)` 的排序规则是：先按 `a` 排，`a` 相同再按 `b` 排，`a、b` 相同再按 `c` 排。所以查询条件必须**从最左列开始**，并且不能跳过中间列，才能充分利用索引。

它像电话簿：先按姓排，同姓再按名字排，你不知道姓，就没法用名字那一层去查。

为什么范围列会中断后面的列？因为 B+ 树只保证「前面的列有序」——`idx_abc(a,b,c)` 里，当 `a` 确定、`b` 取一个范围时，这些行对应的 `c` 在树里是乱序的，没法继续用 `c` 缩小定位，只能扫出来再过滤。

实测（MySQL 8.0.12，`EXPLAIN` 看 `type` 和 `key_len`，索引 `idx_abc(a,b,c)` 三列都是 INT，每列 5 字节）：

```text
WHERE a = 1                      → type=ref,   key_len=5   只用 a 定位
WHERE a = 1 AND b = 2            → type=ref,   key_len=10  a+b 定位
WHERE a = 1 AND b = 2 AND c = 3  → type=ref,   key_len=15  a+b+c 全定位
WHERE a = 1 AND b > 2 AND c = 3  → type=index, key_len=15  范围后 c 失效，退化成全索引扫描
WHERE b = 2                      → type=index, key_len=15  跳过最左列，全索引扫描
WHERE a = 1 AND c = 3            → type=ref,   key_len=5   跳过 b，只有 a 定位
```

两条铁律记住就行：① 必须从最左列开始；② 中间不能断，且**范围列之后全失效**——`b > 2` 之后的 `c = 3` 只能等扫描时过滤（`Extra: Using where`），没法缩小定位范围。

## 五、EXPLAIN 怎么看：type、key_len、Extra 三把尺

判断索引用得好不好，`EXPLAIN` 是绕不开的工具。它输出的字段很多，重点抓三个：

**type —— 访问类型，从好到差**

```text
const > eq_ref > ref > range > index > ALL
```

- `ref`：用索引**精确定位**，走 B+ 树查找，是日常查询里最理想的类型之一。
- `range`：范围扫描，比如 `b > 2` 这种条件。
- `index`：全索引扫描——虽然扫的是索引树，但没有「定位」，只是顺着叶子链表从头扫到尾。
- `ALL`：全表扫描，连索引树都没用上。

其中 `const` 是主键等值查询（最多命中一行）、`eq_ref` 是唯一索引等值连接，单表查询里最常见、也最该争取的就是 `ref`。

前面实测里，`WHERE b = 2`（跳过最左列）时 `type` 从 `ref` 掉到 `index`，就是索引「没定位、只能扫」的信号——比 `ALL` 好一点（索引树更小），但远不如 `ref`。

**key_len —— 命中了几列**

`key_len` 是这次查询实际用到的索引字节数。联合索引里它最能说明问题：`idx_abc(a,b,c)` 三列各 5 字节，`key_len=5/10/15` 分别对应命中一、二、三列。看到 `key_len` 没满 15，就知道有列没用上。

**Extra —— 有没有回表、要不要过滤**

- `Using index`：覆盖索引，不回表。
- `Using where`：索引扫完后还要再过滤一遍。
- `NULL`（空）：要回表取整行。

把这三把尺对上，`EXPLAIN` 里绝大多数「为什么慢」都能定位到具体环节。

## 六、主键为什么建议短、自增、有序

聚簇索引的叶子存的是整行数据，主键就是这棵树的排序键。主键怎么选，会连锁影响所有索引：

**要短**：二级索引的叶子存的是「索引列 + 主键值」，主键越长，每一张二级索引都跟着变大。一个 `BIGINT`（8 字节）主键和一个 `VARCHAR(64)` 主键，这个差距会复制到建在它上面的所有二级索引里。

**要自增、有序**：自增主键的新数据总是追加在树的最右边，是顺序写入；而随机主键（比如 UUID）的新数据会插到树的中间，一页塞不下就要**页分裂**——一页拆成两页，既产生碎片，又让树变深、查询变慢。

所以「主键用自增 `BIGINT`」不是洁癖，是在给聚簇索引和所有二级索引同时减负。

## 小结

- 索引慢，多半不是「没加索引」，而是没理解回表和最左前缀。
- B+ 树「数据全在叶子、叶子串链表」，换来树矮、范围查询快。
- 主键是聚簇索引，叶子存整行；二级索引叶子只存「索引列 + 主键」，查别的列要回表。
- 覆盖索引 = 查询列全在索引里，`Using index` 不回表。
- 联合索引最左前缀：从左往右连续匹配，范围条件会中断后面的列。
- 看 `EXPLAIN` 抓三处：`type` 看访问方式、`key_len` 看命中几列、`Extra` 看回不回表。

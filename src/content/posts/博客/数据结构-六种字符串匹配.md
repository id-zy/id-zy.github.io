# 六种字符串匹配：比较次数最少，不等于跑得最快

「在文本里找一个子串」看起来是个小问题，但它是唯一一个「教科书算法和工业实现差 50 倍」的基础问题——而且差的原因不是复杂度，是常数。

这篇把六种经典算法放在同一台机器、同一批数据上跑：暴力（BF）、KMP、Boyer-Moore、Horspool、Sunday、Rabin-Karp。每条结论都有实测数字，包括三个会推翻直觉的结果。

## 一、暴力匹配：慢在「回退」这两个字

```python
def brute(T, p):
    n, m = len(T), len(p)
    i = 0
    while i <= n - m:
        j = 0
        while j < m and T[i + j] == p[j]:
            j += 1
        if j == m:
            return i
        i += 1          # 失配：起点只右移一位，j 归零重来
    return -1
```

复杂度 O(n·m)，但关键不是这个乘积，而是**「失配之后已经匹配的那部分信息全丢了」**。

举个具体的例子：文本 `aaaaab`、模式 `aaab`。

```text
第 1 次对齐:  a a a a a b
              a a a b
              ✓ ✓ ✓ ✗       3 个字符白比了
第 2 次对齐:  a a a a a b
                a a a b
                ✓ ✓ ✓ ✗     又是 3 个字符白比
```

第一次已经确认了「前 3 个都是 a」，这个事实在第二次对齐时**完全没用上**，又从头比了一遍。所有改进算法都在解决这一件事：**怎么把已匹配的信息变成下一步的跳转依据**。

## 二、KMP：把「已匹配的前缀」变成跳转表

### next 数组到底存什么

KMP 的定义是：`next[j]` = 子串 `p[0..j]` 的**最长相等前后缀长度**（不含自身）。

以 `p = ababaca` 为例：

```text
next(ababaca)  = [0, 0, 1, 2, 3, 0, 1]
next(aaaaab)   = [0, 1, 2, 3, 4, 0]
next(abcabcabcd)= [0, 0, 0, 1, 2, 3, 4, 5, 6, 0]
```

读 `ababaca` 的第 5 位（下标 4，字符 `a`）：子串 `ababa` 的最长相等前后缀是 `aba`，长度 3——`ababa` 的前缀 `aba` 和后缀 `aba` 相同。这就是 `next[4] = 3`。

**这个数字有什么用？** 当 `p[5]`（`c`）失配时，说明文本里已经出现了 `ababa` 这个片段。既然 `ababa` 的前缀和后缀都是 `aba`，那就不必从 `p[0]` 重来——直接把模式串对齐到「`aba` 正好是刚才那个后缀」的位置，从 `p[3]` 继续比。**文本指针 i 一步都不用退**。

### 代码

```python
def kmp_next(p):
    m = len(p)
    nxt = [0] * m
    left = 0                       # 当前已知的最长相等前后缀长度
    for right in range(1, m):
        while left > 0 and p[left] != p[right]:
            left = nxt[left - 1]   # 失配就退到次长的前后缀
        if p[left] == p[right]:
            left += 1
        nxt[right] = left
    return nxt

def kmp(T, p):
    n, m = len(T), len(p)
    nxt = kmp_next(p)
    j = 0
    for i in range(n):
        while j > 0 and T[i] != p[j]:
            j = nxt[j - 1]         # 模式串跳，文本指针不动
        if T[i] == p[j]:
            j += 1
        if j == m:
            return i - m + 1
    return -1
```

两个 `while` 里的 `left = nxt[left-1]` / `j = nxt[j-1]` 是 KMP 的全部精髓：**失配时退到「次长的相等前后缀」，而不是退到 0**。

### 为什么是 O(n+m) 而不是 O(n·m)

看起来有两个嵌套的 `while`，很像 O(n·m)。但注意：`j` 每次成功匹配 +1，每次失配至少减 1，而 `j` 永远不超过 m。所以**整个匹配过程里 `j` 的总增量 ≤ n，总减量也 ≤ n**，`while` 的总执行次数被 n 卡死。这和单调栈的均摊分析是同一个套路：**判据是「每个指针总共走了多少步」，不是循环嵌套层数**。

### 常被搞混的一件事

有的教材用「`next[j]` = 失配后 j 应该跳到哪」的定义，值域是 `[-1, m-1]`，和本文「最长相等前后缀长度」差一位。**两套都对，但混用必错**。看到 KMP 代码先确认它用哪套，再看 `j = next[j]` 还是 `j = next[j-1]`。

## 三、BM：从右往左比，一次跳一大截

BM 敢「跳」，靠的是两个规则，而且它**从模式串末尾开始往前比**——这一点决定了它和 KMP 完全不同的性能特征。

### 坏字符规则（Bad Character）

失配时看文本里那个「坏字符」`c`（对齐在 `p[j]` 位置上的 `T[i+j]`）：

- 如果 `c` 在模式串里出现过，且最右出现在位置 `k`，那么可以把模式串右移 `j - k` 位，让 `c` 和 `p[k]` 对齐；
- 如果 `c` 根本没出现过，**整个模式串可以直接跳过这个字符**，右移 `j + 1` 位。

### 好后缀规则（Good Suffix）

坏字符规则有时会「倒退」（`k > j` 时算出负位移），所以还要一条：已经匹配上的后缀在模式串里**别的地方也出现过**，就把模式串移到那个位置。

两条规则各算一个位移，**取最大值**：

```python
i += max(j - btable.get(T[i + j], -1), gtable[j])
```

### 为什么 BM 平均 O(n/m)

理想情况下，每次比较都失配在最后一个字符上，而且那个字符不在模式串里——于是一次比较就能跳过 m 个字符。**平均每个字符只需要看一次，所以是 O(n/m)**，比 KMP 的 O(n) 还少一个数量级。

实测（随机文本 n=20 万、m=8）：

```text
BM 29,874 次字符比较      KMP 199,988 次
```

**BM 少了 6.7 倍**，就因为它是「跳着走」而不是「一个一个走」。

## 四、Horspool 与 Sunday：BM 的两个轻量版

### Horspool：只留坏字符规则

Horspool（1980）砍掉了好后缀规则，只保留坏字符规则，并且固定**看窗口的最后一个字符** `T[i]`（`i` 是模式串末尾对齐的位置）。

```python
def horspool(T, p):
    n, m = len(T), len(p)
    move = {}
    for i in range(m - 1):          # 注意：不含最后一个字符
        move[p[i]] = m - 1 - i
    i = m - 1
    while i < n:
        k = m - 1
        while k >= 0 and T[i - (m - 1 - k)] == p[k]:
            k -= 1
        if k < 0:
            return i - m + 1
        i += move.get(T[i], m)      # 不在模式串里 -> 直接跳 m
    return -1
```

位移表的构造有个容易写错的细节：**循环到 `m-2` 就停**，不含最后一个字符。因为「末尾字符自己」失配时应该跳 m（整串前移），如果把它写进表里，值会是 0，直接死循环。

### Sunday：看窗口的**后一个**字符

Sunday（1990）改了一处：失配时看的不是窗口末尾，而是**窗口后面那个字符** `T[i+m]`。

```python
step = m - last.get(T[i + m], -1)   # 存在 -> m - 最右位置；不存在 -> m+1
```

为什么这样更好？因为 `T[i+m]` 是**下一次对齐时必然要参与比较的字符**。如果它不在模式串里，说明无论如何都匹配不上，可以直接跳过 `m+1` 位。Horspool 看的是窗口末尾（已经在窗口内，可能刚好匹配），Sunday 看的是「下一格」，信息更超前。

实测（随机文本、m=8）：

| | 字符比较次数 | 耗时 |
| :--- | ---: | ---: |
| Horspool | 29,867 | 4.00 ms |
| Sunday | **27,146** | 4.12 ms |

比较次数少 9%，但墙上时间反而略慢——因为 Sunday 的比较是**从左往右**的，而 Horspool 是**从右往左**的。这个方向差异在下一节会变成一个巨大的性能鸿沟。

## 五、Rabin-Karp：把字符串比较降到 O(1)

思路完全不同：不比字符，**比哈希**。

把长度 m 的子串看成一个 d 进制数：

```text
H("abc") = a·d² + b·d + c
```

相邻子串的哈希可以**滚动**更新（O(1)）：

```text
H(T[i+1 .. i+m]) = (H(T[i .. i+m-1]) - T[i]·d^(m-1)) · d + T[i+m]
```

于是整个匹配变成：算一次模式串哈希，然后让窗口滑过去，每一步只做几次乘加取模。

```python
def rabin_karp(T, p, d=256, q=1_000_000_007):
    n, m = len(T), len(p)
    hp = ht = 0
    for i in range(m):
        hp = (hp * d + ord(p[i])) % q
        ht = (ht * d + ord(T[i])) % q
    power = pow(d, m - 1, q)          # 预计算 d^(m-1) % q
    for i in range(n - m + 1):
        if hp == ht:                  # 哈希相等 -> 逐字符核验，排除冲突
            if T[i:i + m] == p:
                return i
        if i < n - m:
            ht = (ht - power * ord(T[i])) % q     # 减去最高位
            ht = (ht * d + ord(T[i + m])) % q     # 加上新的最低位
    return -1
```

### 哈希冲突的代价，可以用模数实测

`q` 越小，冲突（伪命中）越多，每次伪命中都要 O(m) 逐字符核验，最坏就退化成 O(n·m)。实测（同一文本、m=8）：

```text
q=13          结果=199900  字符比较=16124   伪命中=15478
q=101         结果=199900  字符比较=2038    伪命中=1951
q=1000000007  结果=199900  字符比较=8       伪命中=0
```

**q=13 时几乎每个位置都伪命中**，字符比较从 8 涨到 16124——Rabin-Karp 的全部优势都被冲突吃掉了。这就是「必须选大质数模」的实证，不是理论洁癖。

### RK 的独特价值：多模式串

单模式串匹配里 RK 基本打不过 BM 系。但它有个别人没有的能力：**一次扫描同时匹配多个模式串**——给每个模式算一个哈希，扫一遍文本，每个位置同时比对 k 个哈希。检测抄袭、敏感词过滤这类「k 个模式」的场景，RK 是最自然的方案。

## 七、三个反直觉的读数

### 1. RK 的比较次数最少，却几乎总是最慢

A 场景里 RK 只做了 **8 次**字符比较（一次哈希命中、一次核验成功），是 BF 的 1/26000。但它的耗时是 **28.7 ms**，比 BM 慢 5 倍。

原因：**字符比较次数不等于时间**。RK 每滑一格要做一次乘、一次减、两次取模，每次都是 Python 的大整数运算；而 BM 滑一格只是查一次字典。在解释型语言里，一次算术运算的成本远高于一次比较。

这条结论对所有「算术密集 vs 比较密集」的算法都成立——**评估算法常数项时，要看「每步做几件事」，不是「做了几步」**。

### 2. 全 a 文本下，Sunday 比 Horspool 慢 3 倍（799,976 vs 199,993）

这不是跳跃规则的问题，是**比较方向**的问题：

- Horspool **从右往左**比。模式是 `aaaaaaab`，第一个比较就是 `T[i+7]` vs `'b'`——立刻失配，每格只花 **1 次**比较。
- Sunday **从左往右**比。前 7 个 `a` 全都匹配，第 8 个才失配，每格要 **8 次**比较。

两边移动步数其实一样（Sunday 的 `step = m - last['a'] = 8-6 = 2`，Horspool 是 `step = m-1-6 = 1`…… Sunday 移动更多，但因为每格比较多，反而更慢）。

**教训**：评估一个匹配算法，要同时看「每格比较几次」和「每格移多远」，只算移位距离会得出错误结论。

### 3. 手写 Python 不可能赢过 `str.find`

```text
场景 A：最好的手写 4.00 ms   str.find 0.09 ms     差 44 倍
场景 D：最好的手写 1.35 ms   str.find 0.026 ms    差 52 倍
场景 B：最好的手写 24.22 ms  str.find 0.51 ms     差 47 倍
```

`str.find` 在 CPython 里叫 **fastsearch**，它是：

1. 两字符 Bloom 过滤器（先看「这两个字符是否可能出现在模式里」，一句话排除大部分位置）；
2. 短模式用 memchr + 逐字符（memchr 是 SIMD 优化的 C 函数）；
3. 长模式用 Crochemore-Perrin 的 **Two-Way 算法**（最坏 O(n)，且常数极小）。

而且它全程用 C 跑，不受 Python 的解释器开销拖累。**理解算法是为了知道「什么时候该换策略」，不是为了手写一个能赢过标准库的实现**。

## 八、手写时最容易踩的四个坑

这些都是我自己笔记里真实出现过的 bug，修完才跑通。

### 坑 1：暴力匹配把返回值写进了循环

```python
while i < n and j < m:
    if T[i] == p[j]:
        i += 1; j += 1
    else:
        i = i - j + 1; j = 0
    if j == m:
        return i - j
    else:
        return -1        # ← 灾难：第一次迭代就返回了
```

`return -1` 必须在 `while` **外面**。写成这样，函数永远只跑一趟就返回，输入稍微长一点就报错。

### 坑 2：RK 的滚动更新减错了串

```python
hash_t = (hash_t - power * ord(p[i])) % q    # 错：减的是模式串的字符
hash_t = (hash_t - power * ord(T[i])) % q    # 对：要减掉离开窗口的文本字符
```

移出窗口的是 `T[i]`，不是 `p[i]`。这个错误很隐蔽——只有在「模式串恰好和文本前几位相同」时才可能碰巧不出错，大部分输入下会得到错误结果。

### 坑 3：Horspool 位移表把末尾字符也写进去

```python
for i in range(m - 1):        # 对：0 .. m-2
for i in range(m):            # 错：会把 p[m-1] 也写进表，值为 0，死循环
```

`move[p[m-1]] = m-1-(m-1) = 0`，位移 0 意味着原地踏步。

### 坑 4：KMP 的 next 用错版本

`j = next[j]` 和 `j = next[j-1]` 对应两套不同的 next 定义。抄代码时只抄一半，就会数组越界或者少跳/多跳一位。**判断方法**：看 next[0] 是 0 还是 -1——是 0 就用 `next[j-1]`，是 -1 就用 `next[j]`。

## 九、怎么选

```text
需要保证最坏 O(n+m)？
├─ 是 → KMP（文本流、不可回退的输入，比如网络包逐字节到达）
└─ 否 → 模式串长吗？
         ├─ m ≥ 16 → BM / Horspool / Sunday（跳得远，平均 O(n/m)）
         └─ m 小 → Sunday（看窗口后一个字符，跳跃略大）
多模式串？
└─ 是 → Rabin-Karp（一次扫描同时比 k 个哈希）
生产环境？
└─ 用 str.find / std::string::find / memmem（都比你手写的快一个数量级）
```

三条补充：

- **「文本指针不回退」不是 KMP 独有的**。BM、Horspool、Sunday 的起点 `i` 也是单调前进的，区别在于它们要**随机访问窗口内的 `T[i+j]`**，所以流式输入时必须缓存一整个 m 长度的窗口；KMP 只需 `T[i]` 一个字符，天然适合「逐字节到达」的场景。KMP 真正的硬优势是**最坏也 O(n+m)**，而 BM 系最坏 O(n·m)。
- **字符集小的时候，BM 系优势变小**。DNA（4 字母）场景实测：Horspool 0.15 ms vs BF 0.59 ms，只差 4 倍；26 字母场景差 5 倍；如果把字符集放大到 256（字节流），BM 系的跳跃会更明显。
- **`m` 很大时预处理不划算**。BM 的好后缀表是 O(m)，如果只匹配一次短文本，预处理成本可能超过收益。

## 十、小结

- **暴力匹配慢在「失配后信息全丢」**：已经比过的字符，换个对齐位置又从头比一遍。
- **KMP 的 next[j] = 最长相等前后缀长度**：失配时退到「次长」，文本指针不动。O(n+m) 的证明靠均摊——`j` 的总增量 ≤ n，所以内层 while 不改变复杂度。
- **BM 从右往左比 + 两条规则取最大值**，平均 O(n/m)。实测比 KMP 少 6.7 倍字符比较。
- **Horspool 只留坏字符规则，Sunday 改看窗口后一个字符**。位移表要循环到 `m-2`，含末尾字符会死循环。
- **RK 用滚动哈希把比较降到 O(1)**，代价是哈希冲突：q=13 时伪命中 15478 次、字符比较 16124 次；q=10⁹+7 时降为 0 次伪命中。**模数大小是可实测的工程参数**。
- **三个反直觉**：① RK 比较次数最少（8 次）却最慢（28.7 ms），因为算术比比较贵；② 全 a 文本下 Sunday 比 Horspool 慢 3 倍，原因是比较方向而非跳跃规则；③ 手写 Python 稳定输给 `str.find` 44~52 倍。
- **实践结论**：理解算法用来做选型判断，实现用标准库。

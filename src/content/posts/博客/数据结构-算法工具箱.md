# 算法工具箱：六种把重复计算变成预处理的技巧

前面几篇讲的都是「一个主题讲透」：排序、字符串匹配、树、图。这一篇不一样，它收的是一批**不属于任何单一主题、但每个都要会**的技巧。

把它们放在一起不是凑数。这六个东西有一个共同的形状：**先花一次代价建好某个结构，之后每次查询都变便宜**。二分是「有序」这个结构让每次查询变便宜；埃氏筛是提前建表让每次判素数变便宜；字典树是把公共前缀只存一遍；滚动哈希是让相邻窗口的指纹只差一步。

反过来看，它们的边界也惊人地一致：**预处理只有在查询次数足够多时才划算**。这句话听起来像废话，但下面每一个工具都能给出一个具体的「在哪一点上不划算」的数字。

## 一、这一组工具的共同点

先看全景。左边是「一次性代价」，右边是「每次省下什么」：

| 工具 | 一次性代价 | 每次省下什么 | 什么时候不划算 |
| :--- | :--- | :--- | :--- |
| 二分查找 | 排序 O(n log n) | 查找 O(log n) 而非 O(n) | 只查一次 |
| 快速幂 | 无（本身就是算法） | n 次乘法压成 log n 次 | 指数很小 |
| 埃氏筛 | 建表 O(n log log n) | 判素数 O(1) 而非 O(√n) | 只判几个数 |
| 字典树 | 插入 O(总字符数) | 前缀查询 O(L) 与词库无关 | 只查完整词（哈希表更快） |
| 滚动哈希 | 算最高位权重 O(log m) | 每窗口 O(1) 而非 O(m) | 窗口很短、命中率高 |
| 递归 | 无 | 代码短、结构清晰 | 深度可能上千 |

最后一列比前面三列都重要。教科书只讲「这个算法是 O(log n)」，不讲「它在什么规模下还不如暴力」——而工程上真正需要判断的恰恰是后者。

顺带说一句：字符串是这一组里唯一一个「容器」而非「技巧」的概念，它的核心操作（比较、查找、匹配）在六种字符串匹配那一篇里已经展开过，本篇只在需要时引用。

## 二、二分查找：log n 是「有序」买来的

二分的代码短到不需要解释，但它的**前提**常被跳过：数组必须有序。而有序不是天上掉下来的——排序要 O(n log n)，比二分的 O(log n) 贵得多。

所以二分的真实成本结构是：**如果你只查一次，排序加二分还不如线性扫描**。它的价值在「同一份数据要查很多次」。

```python
def binary_search(nums, target):
    """闭区间 [lo, hi]，找不到返回 -1"""
    lo, hi = 0, len(nums) - 1
    while lo <= hi:
        mid = lo + (hi - lo) // 2      # 防溢出写法
        if nums[mid] == target:
            return mid
        if nums[mid] < target:
            lo = mid + 1
        else:
            hi = mid - 1
    return -1
```

实测一张有序表查 200 次（单位 ms）：

| n | 线性查找 | 手写二分 | `bisect` | 加速 |
| ---: | ---: | ---: | ---: | ---: |
| 10,000 | 22.56 | 0.174 | 0.039 | 129 倍 |
| 100,000 | 243.07 | 0.194 | 0.046 | **1,253 倍** |

前两列的形状才是重点：n 涨 10 倍，线性查找涨 10 倍（22.56 → 243.07），二分几乎不动（0.174 → 0.194）。**这就是 O(n) 与 O(log n) 的差别在数字上的样子。**

第三列值得单独看一眼：`bisect` 比手写快 4 倍多。它是 C 实现的，省掉了整个 Python 循环。所以工程上直接 `import bisect`，手写只在需要自定义比较逻辑时才有意义。

## 三、二分的边界：四种写法，两种会错

二分是「思路三句话、边界调半天」的典型。我把四种常见写法在 0..99 上逐个查找，看谁漏解：

```python
def bs_closed(nums, target):
    """标准：闭区间 [lo, hi]"""
    lo, hi = 0, len(nums) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if nums[mid] == target:
            return mid
        if nums[mid] < target:
            lo = mid + 1
        else:
            hi = mid - 1
    return -1

def bs_half_open_bug(nums, target):
    """错法：闭区间语义却写 lo < hi —— 会漏掉最后一个候选"""
    lo, hi = 0, len(nums) - 1
    while lo < hi:
        mid = (lo + hi) // 2
        if nums[mid] == target:
            return mid
        if nums[mid] < target:
            lo = mid + 1
        else:
            hi = mid - 1
    return -1

def bs_no_plus_one_bug(nums, target, limit=200):
    """错法：更新写 lo = mid，少了 +1 —— 会卡死在同一个 mid"""
    lo, hi = 0, len(nums) - 1
    steps = 0
    while lo <= hi:
        steps += 1
        if steps > limit:      # 死循环保护，正常二分最多 7 步（n=100）
            return "LOOP"
        mid = (lo + hi) // 2
        if nums[mid] == target:
            return mid
        if nums[mid] < target:
            lo = mid           # 少了 +1
        else:
            hi = mid - 1
    return -1
```

结果（在 0..99 上查每一个值，共 100 次）：

| 写法 | 结果 |
| :--- | :--- |
| 闭区间 `lo <= hi` | 0 个漏解 ✓ |
| 闭区间错写成 `lo < hi` | **漏解 37 个**（1, 4, 7, 10, 13, 16…） |
| 更新写成 `lo = mid` | **33 个卡死**，第一个卡死的是查 1 |
| `mid = lo + (hi - lo) // 2` | 0 个漏解 ✓ |

第二行最阴险。`lo < hi` 会让循环在区间只剩一个元素时提前退出，漏掉的正好是那些位置。漏解分布看起来毫无规律（1、4、7、10——间隔 3，因为 mid 每次都落在三等分点上），所以很难靠「试几个数」发现。

第三行在 Python 里表现为**死循环**：`lo = mid` 之后 mid 算出来还是同一个值，永远出不去。我给它加了 200 步上限才测出结果，否则脚本直接挂住——我第一次跑这个实验时就被卡了三分钟。

防溢出的 `lo + (hi - lo) // 2` 在 Python 里其实不必要（整数无上限），但在 C / Java 里 `(lo + hi)` 超过 2^31 就会变负数。**这是少数「写了没用但不写会死」的写法**，跨语言时最好养成习惯。

## 四、快速幂：把指数按二进制拆开

`a^n` 朴素要做 n 次乘法。快速幂的全部依据是一句话：**a 的 2^k 次幂可以靠前一个平方拿到**。

把 n 按二进制拆开，只有那些为 1 的位才真正进入乘积。于是算法变成两条线并行：一边把底数不断平方得到 a^1、a^2、a^4、a^8……，一边看 n 的最低位决定要不要把它乘进答案。

```python
def fast_pow(a, n, m):
    """迭代版：a^n mod m，O(log n)"""
    result = 1
    base = a % m
    while n:
        if n & 1:                  # 这一位是 1，收进答案
            result = result * base % m
        base = base * base % m     # 平方，准备下一位
        n >>= 1
    return result

def fast_pow_rec(a, n, m):
    """递归版：n 偶时 (a^(n/2))^2，n 奇时再乘一个 a"""
    if n == 0:
        return 1
    half = fast_pow_rec(a, n // 2, m)
    if n % 2 == 0:
        return half * half % m
    return a * half * half % m
```

模 10^9+7、指数递增，实测（单位 ms）：

| 指数 n | 朴素乘法次数 | 快速幂循环次数 | 朴素 | 迭代 | 递归 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 10,000 | 10,000 | 28 | 0.37 | 0.001 | 0.002 |
| 100,000 | 100,000 | 34 | 4.30 | 0.002 | 0.002 |
| 1,000,000 | 1,000,000 | 40 | 36.83 | 0.002 | 0.002 |

第三、四列的形状最漂亮：指数涨 100 倍，朴素也涨 100 倍；快速幂的循环次数只从 28 涨到 40——**因为它跟着 log₂n 走**。n=10^7 时朴素要 368.0 ms，快速幂 0.002 ms，差 **19 万倍**。

递归版在这组数据上只慢一点点（0.002 vs 0.002），因为递归深度是 log n ≈ 20 层，函数调用开销被稀释了。但递归写法的 `n // 2` 必须整除——误写成 `n / 2` 会变浮点，指数超过 2^53 后开始丢精度，而且**不报错**。

这套思想能推广到任何满足结合律的运算：把「乘法」换成「矩阵乘」，就是求线性递推第 n 项的矩阵快速幂（斐波那契 O(log n)）。

## 五、埃氏筛：一次建表换无数次查询

判断一个数是不是素数，试除法要 O(√n)。判断 n 以内的素数个数，试除法要 O(n√n)——太慢了。埃氏筛反过来做：**不是判断每个数，而是划掉每个素数的倍数**。

```python
def sieve(n):
    """返回长度为 n 的字节表，is_p[i] 为 1 表示 i 是素数"""
    if n < 2:
        return bytearray()
    is_p = bytearray([1]) * n
    is_p[0] = is_p[1] = 0
    for i in range(2, int(n ** 0.5) + 1):
        if is_p[i]:
            # 从 i*i 开始划，步长 i；切片赋值把循环交给 C 层
            is_p[i * i::i] = bytearray(len(range(i * i, n, i)))
    return is_p
```

两个细节决定它快不快：

**内层从 `i*i` 开始**，不是 `2*i`。因为 `2i, 3i, …, (i-1)i` 早被更小的素数划掉了，从 `i*i` 起才开始有「新」的合数。

**用切片赋值而不是 `for` 循环**。`is_p[i*i::i] = ...` 把整段划掉的动作交给 C 层的步长切片，比 Python 层逐个赋值快近一个数量级。这是 Python 写筛法的关键技巧，很多人不知道。

实测（bytearray + 切片）：

| N | 建表耗时 | 质数个数 |
| ---: | ---: | ---: |
| 100,000 | 1.46 ms | 9,592 |
| 1,000,000 | 1.79 ms | 78,498 |
| 10,000,000 | 39.01 ms | 664,579 |

N 从 10^5 涨到 10^6，耗时几乎不变（1.46 → 1.79 ms），涨到 10^7 才到 39 ms——这就是 O(N log log N) 里那个 log log 的效果，它几乎是个常数。

真正体现价值的是**查表 vs 试除**：查 2 万次「x 是不是素数」，查表 0.52 ms，逐个试除 77.38 ms——**慢 150 倍**。而且查询次数越多，差距按比例拉大。

这也说明了筛法的适用边界：**只判一两个数时，试除更快**（不用建 10 MB 的表）。它就是为「批量查询」设计的。

## 六、字典树：共享前缀，也共享代价

字典树（Trie）把字符串集合按字符逐层展开，公共前缀只存一遍。插入和查询都是 O(L)，**与词库规模无关**——这是它的卖点。

```python
class TrieNode:
    __slots__ = ("children", "is_end")

    def __init__(self):
        self.children = {}
        self.is_end = False

class Trie:
    def __init__(self):
        self.root = TrieNode()

    def insert(self, word):
        cur = self.root
        for c in word:
            if c not in cur.children:
                cur.children[c] = TrieNode()
            cur = cur.children[c]
        cur.is_end = True

    def search(self, word):
        """查完整词：路径要走完，且末节点必须标记为单词结尾"""
        cur = self.root
        for c in word:
            if c not in cur.children:
                return False
            cur = cur.children[c]
        return cur.is_end

    def starts_with(self, prefix):
        """查前缀：路径存在即可，不看 is_end"""
        cur = self.root
        for c in prefix:
            if c not in cur.children:
                return False
            cur = cur.children[c]
        return True
```

`search` 和 `starts_with` 只差最后一行——但这一行决定了「app」和「apple」的区别。这个区分是 Trie 面试题的高频错点。

实测 10 万个长度 8 的随机词（去重后 99,711 个）：

| 操作 | Trie | 对照 | 结论 |
| :--- | ---: | ---: | :--- |
| 插入 10 万词 | 185.28 ms | — | — |
| 查 5 万次完整词 | 42.25 ms | `set` 2.02 ms | **set 快 20.9 倍** |
| 200 个前缀查询 | 0.03 ms | 逐词 `startswith` 扫描 2.43 ms | **Trie 快 84 倍** |

第一行和第三行的对比是本篇最该记住的一条：**Trie 查完整词比 Python 的 `set` 慢 20 倍**。原因不在算法，在常数——`set` 是 C 实现的哈希表，一次哈希就能定位；Trie 是纯 Python 对象逐字符遍历，每个字符都要查一次字典。

所以选 Trie 的判据不是「查找更快」，而是「**需要按前缀检索**」。前缀查询 O(L) 与 50 万词的规模无关，扫描是 O(词数 × L)，这才差出 84 倍。**只要不做前缀，哈希表永远更划算。**

## 七、滚动哈希：相邻窗口只差一步

把字符串看成一个 base 进制的大整数，那滑动一格后，新哈希可以由旧哈希在 O(1) 内推出：减掉最高位的贡献、整体左移一位、新字符补到最低位。

```python
def rolling_hash(text, pattern):
    """返回 pattern 在 text 中首次出现的位置，找不到返回 -1"""
    n, m = len(text), len(pattern)
    if m == 0:
        return 0
    if m > n:
        return -1
    d, q = 31, 10 ** 9 + 7
    high = pow(d, m - 1, q)          # 最高位的权重，只算一次

    hp = 0
    for c in pattern:
        hp = (hp * d + ord(c)) % q

    ht = 0
    for c in text[:m]:
        ht = (ht * d + ord(c)) % q

    for i in range(n - m + 1):
        if ht == hp and text[i:i + m] == pattern:   # 哈希相等还要逐字符确认
            return i
        if i < n - m:
            ht = ((ht - ord(text[i]) * high) * d + ord(text[i + m])) % q
    return -1
```

那句 `text[i:i+m] == pattern` 不能省。哈希相等只是「很可能相等」，虽然 q=10^9+7 时随机碰撞概率约 10^-9，但在构造数据面前它会被打穿。**哈希做初筛、逐字符做终审**，这是滚动哈希的正确用法。

20 万字符文本，比较「每窗口重算」和「滚动更新」（单位 ms）：

| 窗口长度 m | 重算 | 滚动 | 比值 |
| ---: | ---: | ---: | ---: |
| 5 | 56.68 | 19.48 | 2.9 倍 |
| 20 | 202.92 | 26.86 | 7.6 倍 |
| 100 | 1,150.80 | 45.04 | **25.6 倍** |

规律很清楚：**重算的耗时正比于 m，滚动的耗时几乎不变**。

但也别高估它。在六种字符串匹配那一篇的实测里，RK（就是滚动哈希）是六种算法里**最慢**的一个——因为它每个窗口都要做几次大整数取模，而 BM / Horspool 靠「跳着走」根本不做全窗口计算。哈希的强项是「多模式 / 子串集合比对」，不是「单模式最快」。**同一个技巧在不同问题里的性价比可以差一个数量级。**

## 八、递归：所有上面这些的骨架，和它的三条边界

递归本身不是「技巧」，是描述问题的方式。Trie 的遍历、筛法的外层、快速幂的递归版、图的 DFS 全都用它。

```python
def factorial(n):
    if n <= 1:
        return 1
    return n * factorial(n - 1)

def factorial_tail(n, acc=1):
    """尾递归写法：把结果累积到参数里"""
    if n <= 1:
        return acc
    return factorial_tail(n - 1, n * acc)
```

三条硬边界（Python 默认递归上限 1000）：

| 调用 | 结果 |
| :--- | :--- |
| `factorial(500)` | 成功 |
| `factorial(900)` | 成功 |
| `factorial(1200)` | **抛 RecursionError** |
| `factorial(5000)` | **抛 RecursionError** |
| `factorial_tail(900)` | 成功 |
| `factorial_tail(1200)` | **抛 RecursionError** |

后两行是最容易被误解的：**CPython 不支持尾调用优化**。把递归写成尾递归形式（结果累积到参数里），在 Scheme、部分 C 编译器上能变成循环不占栈，在 Python 里一模一样会爆——因为解释器不会做那个变换。

这三次踩坑（本篇、图的那一篇、动态规划那一篇）让我形成了一个固定动作：**只要深度可能上千，直接写迭代**，不试递归再改。

顺带说一个反复验证的结论：递归不比迭代慢多少。10 万顶点的图遍历，递归 30.99 ms、迭代 27.14 ms，只差 14%。**逼你写迭代的是深度上限，不是速度**——这一点和很多人的直觉相反。

## 九、群组测试与香农熵：log n 从哪来、下界在哪

假设 n 个样本里有 1 个次品，每次测试可以测「任意一组里有没有次品」，答案是是/否。逐个测要 n 次，但把一半混在一起测，一次就能排除一半——这就是群组测试。

```python
def group_test_binary(n, defect):
    """二分式自适应群组测试：返回 (次品位置, 测试次数)"""
    lo, hi = 0, n            # 次品在 [lo, hi) 里
    tests = 0
    while hi - lo > 1:
        mid = (lo + hi) // 2
        tests += 1           # 测 [lo, mid) 这一组
        if lo <= defect < mid:
            hi = mid
        else:
            lo = mid
    return lo, tests
```

实测：

| n | 二分群组测试 | 逐个测试 | 省 |
| ---: | ---: | ---: | ---: |
| 1,000 | 10 次 | 1,000 次 | 100 倍 |
| 1,000,000 | 20 次 | 1,000,000 次 | **50,000 倍** |

n 涨 1000 倍，测试次数只从 10 涨到 20——它跟着 log₂n 走。这个方法二战时用于美军梅毒血液筛查，就是这个思路。

有意思的是，20 这个数字不是「差不多够用」，而是**几乎压在下界上**。下一节算一下就知道了。

### 香农熵：为什么有些问题快不了

香农熵衡量的是一件事的「意外程度」，公式是 `H = -Σ p·log₂p`。在这里它只有一个用处：**告诉你这个问题至少需要多少比特的信息**。

「n 个样本里找出 d 个次品」的答案有 C(n,d) 种可能，所以信息量是 log₂C(n,d) 比特；而每次二选一测试最多提供 1 比特。于是测试次数的下界是：

```python
import math

def lower_bound(n, d):
    """群组测试的测试次数下界：log2 C(n, d)"""
    return math.log2(math.comb(n, d))

for n, d in ((1000, 1), (1000, 2), (1000, 5), (10 ** 6, 1), (10 ** 6, 2)):
    print(f"n={n:>9,} d={d}  下界 {lower_bound(n, d):.2f} 比特")
```

| n | d | log₂C(n,d) | 下界（次测试） |
| ---: | ---: | ---: | ---: |
| 1,000 | 1 | 9.97 | 10 |
| 1,000 | 2 | 18.93 | 19 |
| 1,000 | 5 | 42.91 | 43 |
| 1,000,000 | 1 | 19.93 | 20 |
| 1,000,000 | 2 | 38.86 | 39 |

对照上一节的实测：n=1,000,000、d=1 时二分式群组测试用了 **20 次**，下界正是 19.93——**实测值就压在下界上**。

这个巧合说明两件事。一是二分式方案已经最优，再想减少测试次数只能改变「每次测试能提供多少比特」（非自适应方案里的组合编码就是这条路）。二是**下界论证比算法本身更有价值**：它告诉你「这条路走到头了」，省下继续优化的时间。

而这条推理能推广到所有问题：**下界 = 总信息量 ÷ 每次操作能获取的比特数**。比较排序的下界 Ω(n log n) 就是这么来的（n! 种排列，每次比较 1 比特）；很多「为什么快不了」的困惑，答案都在这里——不是没找到好算法，是**信息量本身不够**。

## 十、小结：三句话和一个反直觉数字

如果只能记三句话：

**一、先问「查几次」。** 六个工具里有五个都是「预处理换查询」，预处理只有在查询够多时才值得。二分要排序、筛法要建表、Trie 要插入全部词——都只在重复使用时回本。

**二、选工具看「要做什么操作」，不看「谁更高级」。** Trie 查完整词比 `set` 慢 21 倍，只在前缀查询上快 84 倍；滚动哈希在单模式匹配里是最慢的那个，它的战场在子串集合比对。**同一个结构在不同操作上的相对优劣可以完全相反。**

**三、递归的敌人是深度，不是速度。** 递归比迭代只慢 14%，但 1200 层就爆栈，尾递归也救不了。这个结论在树、图、DP 三个主题上重复出现了三次，已经是可靠的经验。

最后一点体会：这一篇里最有用的数字，不是「快 1253 倍」，而是**「Trie 比 set 慢 21 倍」**。前一种数字告诉你某个方法有多强，后一种数字告诉你**什么时候不该用它**——后者在真的写代码时更有价值。
